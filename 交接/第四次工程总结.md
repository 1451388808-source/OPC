# OPC 第四次工程总结

日期：2026-10-13。

## 结果

第四期“项目群聊即团队工作现场”本机受控版已经完成。实现依据：

- `docs/第四期工程文档.md`
- `docs/第四期实施计划.md`

老板在群聊只发送一条消息。普通交流由自动选择的协调员工接话；任务会创建 workflow，由项目成员按角色生成计划、认领工作项、使用 MCP 工具执行、复核并提交最终验收。

## 协作闭环

```text
群聊任务
  → 结构化计划
  → 工作项依赖调度
  → 员工 MCP 执行
  → 员工复核或返工
  → 必要时等待老板决定
  → workflow 验收
  → 老板批准应用
```

用户待决只阻塞指定工作项及依赖链。老板选择后，决定写入统一事件流，工作项恢复并重新进入后台队列。

## 文件与验证边界

正式项目目录仍为：

```text
workspaces/<companyId>/<projectId>/
```

第四期暂存目录：

```text
.opc/workflows/<workflowId>/
  before/
  after/
  sandbox/
  manifest.json
```

文件写入要求读取基线哈希并持有工作项租约。验证命令来自正式项目的 `opc-validation.json`，使用 `shell: false`、固定沙箱、环境白名单、超时和输出上限。当前没有 OS/容器级网络隔离，验证 profile 不应包含不可信命令；远程 MCP 默认关闭。

## 性能修复

p-001 累积 17,409 条第三期流式执行事件后，统一事件接口曾在每次请求和每个 500ms SSE 轮询中重新扫描全部旧事件，导致事件 API 中位数约 519-740ms，并拖慢看板和公司页。

修复内容：

- 新增 `009_project_event_backfill_state.sql`，按项目保存 message、run 和 run event 的增量高水位。
- 历史回填只查询高水位之后的新记录，不再对完整旧表执行 LEFT JOIN 扫描。
- SSE 建立连接时回填一次，后续轮询只读取 `project_events.id > afterId`。
- 前端预计算已解决待决问题集合，移除事件渲染中的 O(n²) 扫描。
- 增加 `npm run test:perf:events`，预热中位数超过 250ms 时失败。

修复后，在项目 SSE 打开的情况下：

- 看板约 88ms。
- 公司页约 95ms。
- 项目页约 316ms。
- 项目事件 API 约 28-53ms。
