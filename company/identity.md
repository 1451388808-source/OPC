# 身份

角色每次开工先读这一份。这里写的是公司是谁、现在处在哪一期、哪些约束不能被任务临时改掉。

## 公司是什么

OPC 是 Boheng 的一人公司操作系统。它把目标、任务、角色分工和已经拍板的决定放在这个仓库里。同一个人分饰策划、工程、研究和运营时，下次开工仍然从这些文件出发，而不是从聊天记录里重找背景。

现在正在做的产品就是这套系统本身。它还不是对外售卖的服务，也还没有第二个使用者。

## 为谁

当前使用者只有 Boheng，学生，习惯直接在仓库里写代码、改文档、看结果。

他要用这套系统完成的事：一个人推进项目时，目标、正在做的任务和已做的决定都留在仓库里，打开就能继续。

外部客户还没有。在 `customers.md` 的「已接受的事实」出现具体的人之前，角色把使用者当成 Boheng 本人。

## 当前阶段

第一期 · 文件骨架。

这一期做完的样子：`company/` 和 `roles/` 可以被人或代理直接阅读，并有一条任务按状态机走到待批准。本地看板、模型调用、推远程和对外发送属于后面的期，这一期不开工。

阶段要变的时候，先改这一节，再让受影响的 `now` 任务停下来重读目标。

## 硬约束

- 只有一个人。没有同事可以并行接手另一条任务。
- 注意力上限：`priority` 为 `now` 且 `status` 为 `doing` 的任务最多 2 条。
- 公司事实放在 `company/`，工单放在 `tasks/`，职责放在 `roles/`。第一期的存储就是这些文件。
- 文档用中文。角色 id、任务文件名和代码标识符用英文。
- 时区是 Asia/Shanghai。机器可读时间写成带 `+08:00` 的 ISO 8601。
- 下面这些动作要你点头之后才算数：修改本文件、修改 `goals.md`、向 `decisions.md` 或 `customers.md` 写入事实、把草稿标成可发送、`git push`、发布、花钱、对外发消息。
- 课业先于这个仓库。每周能投入的小时数见文末，填写之前按「时间很少」来排期，一条任务只做验收里的事。
- 预算见文末。填写之前，方案里不加入需要付费的 API、托管或订阅。

## 工作语言

对你说话、写公司文档、写任务标题和验收，用中文。

固定用词：

| 说法 | 对应 |
| --- | --- |
| 收件 | `inbox` |
| 进行中 | `doing` |
| 待批准 | `review` |
| 阻塞 | `blocked` |
| 完成 | `done` |

角色不在这里列死。`roles/` 里每一份手册是一个角色：文件名是 id，一级标题是看板上的名字。哪一份负责收下新句子，在该手册开头写 `收件默认: 是`。要加角色，就新加一份手册。

任务文件名是 `t-` 加三位数字，例如 `tasks/t-001.json`。编号只增不复用。

## 工作方式

1. 开工按这个顺序读：本文件、`company/goals.md`、`company/decisions.md` 最近 10 条、当前任务 JSON、该任务角色的手册。
2. 你的一句话先进收件箱。策划把它收成带验收的任务之后，其他角色才开工。
3. 一条任务只有一个主责角色。需要另一个角色时，新开一条任务，在两边的 `notes` 里互相写上 id。
4. `notes` 只追加。每条以 `YYYY-MM-DD HH:mm · 角色 · ` 开头。
5. 验收要能检查。每条只包含一件事：文件是否存在、某一节是否存在、字段是否等于某个值、或者一条命令的输出是什么。
6. 角色可以把任务推到 `review`。把 `status` 写成 `done` 这件事只由你做。
7. 仓库路径用相对路径和正斜杠。
8. 研究笔记写到 `company/notes/YYYY-MM-DD-短标题.md`。运营草稿写到 `company/drafts/YYYY-MM-DD-短标题.md`，第一行写「草稿，尚未发送」。
9. 聊天和 README 里的方案，在 `decisions.md` 出现对应条目之前，都还是草案。

## 待你填写

这三项只有你知道。角色看到仍是下面的占位句时，按占位句执行，不替你补数字或方向。

- 每周可投入在 OPC 上的小时数：待你填写。填写前，本周只推进「本周唯一重点」那一条线。
- 预算上限：待你填写。填写前，不设计付费依赖。
- 这套系统稳定之后，先拿它服务哪类工作：待你填写。可选的方向包括写代码、做内容、课堂或项目交付。填写前，系统只服务「把 OPC 自己做出来」这件事。
