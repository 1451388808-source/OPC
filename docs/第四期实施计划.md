## 1. 执行目标

第四期把项目群聊从“聊天加单员工执行入口”改造成真正的团队工作现场：老板只发送任务，系统组织项目成员分工、执行、复核；员工无法决定的问题以结构化选项交给老板；最终产出由老板统一验收。

最终验收场景以 `docs/第四期工程文档.md` 第 23 节为准。实施必须保持第三期流程可用，直到新协作链完成端到端验收并迁移历史数据。

## 2. 已确定的工程决策

### 2.1 增量迁移

第四期先新增表和模块，不直接删除或改写：

- `project_messages`
- `project_runs`
- `project_run_events`
- `project_run_files`

新任务切换到 workflow 后，旧表进入只读兼容阶段。确认没有活动旧执行后再讨论归档。

### 2.2 三层职责

```text
领域状态机：决定什么状态迁移合法
应用调度器：决定下一位员工和下一项工作
MCP Gateway：决定工具是否允许以及如何审计
```

模型只能提出结构化动作，不能直接更新数据库状态。

### 2.3 协作标识

```text
workflow:         wf-<UUID>
work item:        wi-<UUID>
decision request: dr-<UUID>
artifact:         a-<UUID>
```

编号不依赖全局序列，避免后台并发争用。

### 2.4 MCP 接入顺序

先完成领域模型、持久化和确定性调度，再接 MCP。MCP Server 首版只提供第一方本机工具，外部 Server 默认关闭。

## 3. 工作包

### W0：基线与协作领域

依赖：无。

修改范围：

```text
docs/第四期实施计划.md
db/migrations/007_collaboration.sql
lib/domain/collaboration.ts
lib/domain/collaboration.test.ts
```

步骤：

1. 定义 workflow、work item、event、decision 和 artifact 类型。
2. 实现 workflow 与 work item 合法状态迁移。
3. 实现工作项依赖校验和可执行项计算。
4. 建立第四期全部持久化表，但暂不接页面。
5. 运行现有单元测试和类型检查，确认第三期不回归。

完成条件：

- 合法与非法状态迁移都有测试。
- 自依赖、未知依赖和环形依赖被拒绝。
- 只有依赖全部完成的排队工作项会被选为可执行。
- `007` 迁移可重复执行。

### W1：统一项目事件流

依赖：W0。

修改范围：

```text
lib/infrastructure/collaboration-store.ts
lib/application/project-event.ts
tests/integration/collaboration-store.test.ts
```

步骤：

1. 实现项目事件追加、按项目分页和按 workflow 查询。
2. 每次写入用领域 schema 校验 `kind`、actor 和关联编号。
3. 实现旧项目消息和旧执行事件的只读兼容投影。
4. 统一事件按数据库编号排序，不用客户端时间拼接。
5. 增加 `afterId` 增量查询，供 SSE 恢复使用。

完成条件：

- 普通消息、旧执行和新 workflow 事件能形成稳定顺序。
- 刷新和断线重连不会重复或丢失事件。
- 页面尚未切换时，旧功能行为不变。

### W2：协作任务 Store 与调度器

依赖：W0、W1。

修改范围：

```text
lib/infrastructure/collaboration-store.ts
lib/collaboration/scheduler.ts
lib/application/collaboration.ts
```

步骤：

1. 实现 workflow、work item、依赖、decision 和 artifact Store。
2. 事务内创建 workflow 和初始工作项。
3. 实现无环依赖调度、最大并发和幂等认领。
4. 实现工作项完成、复核、返工、交接和失败恢复。
5. 先使用 Fake Agent 驱动完整协作流程。

完成条件：

- 两名 Fake Agent 可以按依赖完成同一 workflow。
- 服务重启后可从持久化状态继续调度。
- 同一工作项不会被两个员工同时认领。

### W3：群聊单入口与消息路由

依赖：W1、W2。

修改范围：

```text
lib/collaboration/router.ts
app/api/projects/[id]/events/route.ts
app/api/projects/[id]/stream/route.ts
app/company/project-chat.tsx
```

步骤：

1. 输入框改为一个“发送”主动作。
2. 实现普通交流、新任务、任务补充和决策答复分类。
3. 分类结果写入统一事件并在页面可见。

完成条件：

- 普通提问不会启动执行。
- 发任务不需要选择单个员工。
- 刷新后消息、分类和 workflow 状态一致。

### W4：OPC MCP Server

依赖：W2。

修改范围：

```text
mcp/server.ts
mcp/tools/project.ts
mcp/tools/workflow.ts
lib/mcp/client.ts

```

步骤：

2. 使用环境变量白名单启动独立子进程。
3. 实现工具发现、schema 快照和 Server 生命周期。
4. 封装项目文件读取、暂存写入和 diff 工具。
5. 每次调用注入 workflow、work item、role 和 project 上下文。
6. 实现 allow/confirm/deny 权限决策和调用审计。

完成条件：

- 模型执行链不再直接调用 `createProjectFileTools()`。
- 越权路径、伪造员工和禁用工具被 Server 端再次拒绝。
- MCP Server 崩溃后当前调用明确失败，重启不丢 workflow 状态。

### W5：共享暂存与验证沙箱

依赖：W4。

修改范围：

```text
lib/project-workspace/workflow-workspace.ts
mcp/tools/validation.ts
项目验证配置
```

步骤：

1. 暂存目录从 run 级扩展为 workflow 级。
2. 实现文件租约和基于 after hash 的并发写保护。
3. 物化验证沙箱，使命令看到全部候选修改。
4. 命令只接受配置 profile，不接受模型命令字符串。
5. 实现超时、输出上限、进程树取消和环境白名单。

完成条件：

- 两个工作项可并行修改不同文件。
- 同一路径并发写被拒绝并留下事件。

### W6：真实多智能体协作

依赖：W2、W4、W5。

步骤：

1. 定义 Provider 无关的 `AgentAction`。
2. 选择协调员工并生成初始计划。
3. 根据角色和技能分配主责与复核人。
4. 实现认领、异议、证据、交接、复核和自动返工上限。
5. 只把公开工作说明写入事件，不保存原始私有思维链。
6. 对长时间线生成可追溯摘要。

完成条件：

- 至少两名真实员工完成一次分工与交接。
- 无关员工不轮流发言。
- 工具、员工和事件均能追溯到具体工作项。

### W7：用户仲裁与局部恢复

依赖：W2、W6。

步骤：

1. 实现结构化 decision request。
2. 记录选项、推荐、影响和阻塞工作项。
3. 仅暂停依赖该决定的工作项链。
4. 老板答复后写事件并恢复正确工作项。
5. MCP 的 `confirm` 权限复用相同交互。

完成条件：

- 非阻塞工作在等待老板时继续进行。
- 同一决定不会重复询问。
- 回答和采用结果可完整追溯。

### W8：统一验收与看板接入

依赖：W3、W5、W6、W7。

步骤：

1. 汇总验收条件、文件、验证、决定和风险。
2. 群聊中展示验收卡片和完整展开详情。
3. 批准时冲突检查、应用文件并完成关联看板任务。
4. 退回时重开指定工作项，而不是创建失去上下文的新任务。
5. 看板派工改为“交给项目团队”。

完成条件：

- 群聊和看板使用同一 workflow。
- 未批准前正式文件不变。
- 一次批准完成文件应用、workflow 批准和任务完成。

### W9：迁移收口与稳定性

依赖：W0-W8。

步骤：

1. 新任务停止创建 `project_run`。
2. 完成旧消息和执行历史投影或迁移。
3. 增加外部 MCP Server 登记、禁用和 schema 变化确认。
4. 补齐全量安全、恢复和浏览器验收。
5. 更新 README、功能需求和第四次工程总结。

完成条件：

- 第四期最终验收场景全部通过。
- 旧历史可查且无新旧双写漂移。
- 外部 MCP 默认无权限。
