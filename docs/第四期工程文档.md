# OPC 第四期工程文档

版本：2026-10-13  
状态：已完成（本机受控版）  
范围：项目群聊协作执行、多智能体分工、用户仲裁、统一验收、OPC MCP Server

## 1. 背景

第三期已经完成“选择一名员工执行文件任务”的闭环：员工可以读取项目文件、暂存修改、展示差异，并在老板批准后应用到正式目录。

但当前实现仍然没有达到“公司项目群聊就是工作现场”的目标：

- 群聊存在“发送消息”和“执行任务”两个入口，对话与执行是两条流程。
- 老板必须提前指定一名主责员工，系统不会根据角色职责自动组织团队。
- 普通群聊会让员工依次回复，但员工只能说话，不能在同一轮里继续执行。
- 一次 `project_run` 只有一个 `role_id`，其他员工不能认领子任务、交接或复核。
- 员工之间没有明确的协商、异议、决策和阻塞协议。
- 系统没有“这件事必须由老板决定”的结构化状态，只能在文本里提出问题。
- 执行工具直接绑定在应用内部，尚未形成 MCP Server，工具不能被统一发现、授权、审计和扩展。
- 工程员工可以暂存文件，但不能运行受控验证命令，无法用测试结果证明任务真的完成。

第四期要把这些割裂的能力合成一条协作链：老板只需要在项目群聊里发出任务，项目内的智能体员工按照各自职责讨论、分工、执行、复核；只有员工无法自行决定的事项才提交给老板；完成后仍由老板做最终验收。

## 2. 第四期目标

第四期完成后，一条项目任务应能走完下面的闭环：

1. 老板在项目群聊里发出一条任务，不再选择“只聊天”或“执行任务”。
2. 系统把这条消息保存到统一时间线，并判断它是普通交流、任务、补充信息，还是对待决问题的答复。
3. 若消息形成任务，协调员工根据项目成员的角色手册和技能拆出工作项。
4. 相关员工在群聊里说明认领、依赖、异议和交接；无关员工不机械轮流发言。
5. 员工通过 OPC MCP Server 读取上下文、操作项目工作区、暂存文件和运行受控验证。
6. 多个员工可以各自完成工作项，但所有产出属于同一个协作任务，并共享同一份项目事实和事件记录。
7. 员工能用证据解决的分歧自行解决；涉及产品取舍、风险授权或信息缺失时，创建结构化待决问题交给老板。
8. 老板回答后，只恢复依赖该决定的工作项，其他不受影响的工作可以继续。
9. 全部工作项完成后，复核员工按验收条件检查产出，形成验收包。
10. 群聊展示最终摘要、文件差异、验证证据、风险和待批准动作。
11. 老板批准后应用文件并完成任务；退回时保留原因，团队基于原协作上下文继续工作。

第四期的完成标志：老板在群聊里只发一次任务，至少两名不同职责的员工能在同一协作任务中完成“规划或研究 → 实施 → 验证 → 提交验收”，中间若出现无法自行裁决的问题，页面能暂停相关工作并让老板选择，最终由老板一次批准完成。

## 3. 核心原则

### 3.1 群聊是唯一工作入口

项目页不再把“发送消息”和“执行任务”作为两个互斥动作。输入框只保留一个主动作：`发送`。

每条老板消息进入同一个项目事件流。系统根据当前上下文处理为：

- 普通交流：员工在群里回答，不创建协作任务。
- 新任务：创建新的协作任务并开始分工。
- 任务补充：追加到指定的进行中协作任务。
- 决策答复：解决一个待决问题并恢复相关工作项。
- 验收动作：批准、退回或取消协作任务。

分类结果必须在时间线中可见，并允许老板纠正。不能因为模型误判而静默启动高风险执行。

### 3.2 对话和执行使用同一条事件时间线

用户消息、员工发言、任务拆分、工作项状态、工具调用摘要、验证结果、待决问题和最终验收都属于项目群聊事件。

“对话”和“执行”不再是两个页面世界。执行详情仍可作为群聊事件的展开面板，用于查看完整 diff、工具参数、日志和审批信息，但不能要求用户离开群聊才能知道任务进展。

### 3.3 员工按职责参与，不按名单轮流发言

系统根据角色手册、技能和当前工作项选择参与员工。每个工作项只有一名主责员工，可以有复核员工和依赖项。

默认职责示例：

| 职责 | 典型工作 |
| --- | --- |
| 策划 | 澄清目标、拆分工作项、定义验收条件、汇总进度 |
| 研究 | 查找资料、核对事实、提供证据和方案比较 |
| 工程 | 修改文件、实现功能、运行受控验证 |
| 运营 | 检查交付表达、发布准备、面向用户的最终说明 |

角色不是写死的四人名单。实际路由以 `roles/` 手册和员工技能为准。项目中没有某种职责时，协调员工应明确指出能力缺口，而不是假装工作已经被覆盖。

### 3.4 协作编排由系统状态机负责

模型负责提出计划、执行专业工作和给出判断；应用层负责任务状态、依赖关系、并发限制、超时、重试、暂停和恢复。

不能让某个模型仅靠一段提示词无限循环地“管理其他模型”。每一次认领、交接、工具调用、待决问题和状态迁移都必须持久化，并由应用层校验是否合法。

### 3.5 员工先协商，真正无法决定时再找老板

员工意见不一致时按下面顺序处理：

1. 检查是否是事实分歧；能通过文件、测试或可信资料验证的，先补证据。
2. 检查是否已有公司决定、任务验收或角色职责明确规定；已有规则时按规则执行。
3. 检查是否属于某个工作项主责的专业决策；可逆且低风险时由主责决定并记录理由。
4. 涉及产品方向、不可逆操作、预算、对外动作、权限扩大或用户偏好时，提交老板决定。
5. 提交时必须给出选项、差异、推荐项和不决定的影响，不能只问一句开放问题。

### 3.6 老板保留最终验收权

员工可以把工作项标记为完成，复核员工可以把协作任务提交验收，但只有老板能：

- 批准正式文件应用。
- 批准高风险或对外动作。
- 把关联看板任务改为 `done`。
- 将结论写入公司决定。

### 3.7 MCP 是工具边界，不是协作状态机

OPC MCP Server 负责把工具以标准协议提供给员工，并统一做参数校验、权限检查、审计和结果结构化。

协作任务、工作项依赖、用户仲裁和最终验收仍由 OPC 应用层管理。不能把公司的核心工作流隐藏在某个 MCP Server 的进程内存里。

## 4. 本期范围

### 4.1 必须实现

- 项目群聊单一输入入口。
- 普通交流、新任务、任务补充和决策答复的可解释路由。
- 多员工协作任务和工作项模型。
- 按角色与技能自动选择参与员工。
- 工作项认领、依赖、交接、复核和完成。
- 统一项目事件流，覆盖消息、状态、工具、产出、待决和验收。
- 结构化用户待决问题及恢复机制。
- 同一协作任务下的多员工工具执行。
- 协作任务级共享暂存区和文件冲突控制。
- OPC MCP Server。
- OPC 内部 MCP Client 和工具权限网关。
- 项目文件读取、暂存写入、diff 和受控验证工具迁移到 MCP。
- MCP 工具调用审计、超时、取消和结果大小限制。
- 最终验收包和群聊内批准、退回流程。
- 从看板任务进入同一套协作执行流程。
- 旧第三期 `project_run` 数据和页面的兼容迁移。

### 4.2 本期受控实现

- 只允许配置好的验证命令，不开放任意 Shell。
- 外部 MCP Server 先实现登记、禁用、工具发现和逐项授权，不默认信任。
- 同一协作任务允许多个员工参与，但同一路径同时只能有一个有效写入者。
- 并发先限制在少量无依赖工作项，默认最多 2 个员工执行工具。

### 4.3 明确不做

- 智能体自行批准最终结果。
- 无上限的自主循环或无限员工互相对话。
- 默认开放任意本机目录、完整 Shell、管理员权限或用户全部环境变量。
- 自动 `git push`、部署、付费、购买、发邮件或公开发布。
- 未经老板授权连接任意远程 MCP Server。
- 多用户账号、远程协同编辑和复杂组织权限系统。
- 让模型直接读写协作表或绕过应用层改变任务状态。
- 展示或长期保存模型的原始私有思维链；页面只展示工作说明、证据、决定和必要的执行摘要。

## 5. 用户流程

### 5.1 发起任务

1. 老板打开项目群聊。
2. 输入“完成登录页并补测试”这类任务，点击发送。
3. 消息立即进入群聊。
4. 系统标记“识别为新任务”，创建协作任务。
5. 协调员工在群里给出目标、工作项、参与人和验收条件。
6. 各员工开始认领和执行，不要求老板逐个选择员工。

若系统识别为普通交流，只产生回复。消息旁提供“转为任务”；若系统误建任务，老板可以在任何工具执行前改为普通交流或取消。

### 5.2 团队讨论与执行

群聊应展示有工作价值的事件：

- “策划已拆成 3 个工作项”。
- “研究认领竞品核对”。
- “工程依赖研究结论，等待该工作项”。
- “研究提交证据并完成交接”。
- “工程正在读取 4 个文件”。
- “工程暂存修改 2 个文件”。
- “工程运行 `npm test`，18 项通过”。
- “运营完成交付文案复核”。

原始工具输出、完整 diff 和长日志默认折叠。群聊优先展示谁在做什么、为什么、结果是什么以及下一步由谁负责。

### 5.3 用户仲裁

当员工无法自行决定时，群聊插入一个待决卡片：

```text
需要你决定：登录失败后是否锁定账号？

A. 连续 5 次失败锁定 15 分钟
B. 只增加验证码，不锁定

团队推荐：A
理由：满足当前安全目标，但会增加客服处理成本。
影响：未决定前，认证策略工作项暂停；页面布局和测试脚手架继续进行。
```

老板可以点击选项，也可以填写自己的决定。回答会成为结构化事件，并自动恢复依赖该决定的工作项。

### 5.4 提交验收

全部必要工作项完成后，协调员工生成验收包：

- 原始任务和最终范围。
- 参与员工及各自产出。
- 验收条件逐条结果。
- 修改文件和 diff。
- 测试、构建或其他验证证据。
- 已由老板做出的中间决定。
- 尚存风险、未做事项和需批准动作。

群聊出现一个主操作“验收这项工作”。老板可以批准、退回或取消。批准后应用文件并更新关联任务；退回时必须填写原因，由协调员工重新打开相应工作项。

## 6. 统一群聊语义

### 6.1 输入分类

每条老板消息先经过 `ProjectMessageRouter`。输出必须是结构化类型：

```ts
type ProjectMessageIntent =
  | { type: "conversation" }
  | { type: "new_workflow"; title: string }
  | { type: "workflow_input"; workflowId: string }
  | { type: "decision_answer"; decisionId: string }
  | { type: "review_action"; workflowId: string; action: "approve" | "return" | "cancel" };
```

路由规则：

- 明确提问、讨论、解释默认是 `conversation`。
- 包含可交付目标、修改、调查、制作、执行或验收要求时，倾向 `new_workflow`。
- 项目只有一个活动协作任务且消息明显补充该任务时，可路由为 `workflow_input`。
- 存在待决问题时，短答复优先匹配该问题，但必须在页面显示绑定对象。
- 有多个可能目标时，不猜测，先让老板选择关联任务。
- 路由只决定工作流入口，不授予额外工具权限。

### 6.2 统一事件流

项目页按 `project_event.id` 顺序渲染，不再分别拼接 `project_messages` 和 `project_run_events`。

建议事件种类：

```text
user_message
agent_message
workflow_created
workflow_status
work_item_created
work_item_status
handoff
tool_call
tool_result
artifact
decision_requested
decision_resolved
verification
review_submitted
approval
return
error
```

事件包含 `workflow_id` 和 `work_item_id` 时可以展开到对应详情；普通交流事件两者均为空。

### 6.3 可见内容

群聊展示：

- 员工公开发言。
- 简短工作计划和决策理由。
- 工具调用目的、对象和结果摘要。
- 验证证据。
- 阻塞和待决问题。

群聊不展示：

- 模型原始私有思维链。
- 密钥、令牌和完整环境变量。
- 超长命令输出和二进制内容。
- 对完成任务没有帮助的智能体互相寒暄。

## 7. 多智能体协作模型

### 7.1 协调责任

每个协作任务有一个 `coordinator_role_id`。优先选择具备任务拆分或策划技能的项目成员；没有明确协调者时，使用可配置的项目默认员工。

协调者负责：

- 把老板原话收成目标和验收条件。
- 选择需要参与的职责。
- 创建工作项和依赖。
- 发现重复、缺口和冲突。
- 控制讨论轮数。
- 汇总最终验收包。

协调者不能：

- 替专业主责伪造结果。
- 绕过依赖直接把工作项标为完成。
- 替老板批准风险动作和最终结果。

### 7.2 工作项

每个工作项包含：

```ts
type WorkItem = {
  id: string;
  workflowId: string;
  title: string;
  objective: string;
  acceptance: string[];
  ownerRoleId: string;
  reviewerRoleId: string | null;
  status: "queued" | "ready" | "running" | "blocked" | "review" | "done" | "failed" | "cancelled";
  blockedReason: string;
};
```

规则：

- 一个工作项只有一个主责员工。
- 主责必须是项目成员，并具备需要的技能或明确接受能力缺口。
- 工作项依赖满足后才能从 `queued` 进入 `ready`。
- 工作项完成必须提交产出和验收证据。
- 需要复核时，主责不能同时充当唯一复核人。
- 交接会改变主责，但保留原主责、原因和已有上下文。

### 7.3 协作循环

一次协作任务的调度循环：

1. 协调者生成初始工作项计划。
2. 应用层校验成员、依赖环、工作项数量和权限。
3. 相关员工最多进行两轮计划异议；没有新证据时停止重复讨论。
4. 调度器把无依赖工作项设为 `ready`。
5. 员工认领后进入 `running`，通过 MCP 工具执行。
6. 员工提交产出与证据，进入 `review`。
7. 复核通过后进入 `done`；不通过则回到 `running` 并附理由。
8. 新事实可以由协调者追加工作项，但必须记录范围变化。
9. 所有必要工作项完成后，协作任务进入最终 `review`。

### 7.4 讨论限额

- 初始计划讨论最多 2 轮。
- 同一异议在没有新证据时最多重复 1 次。
- 单个工作项最多自动返工 2 次，之后提交协调者或老板处理。
- 每个协作任务默认最多 12 个工作项。
- 同时运行工具的员工默认最多 2 名。
- 员工发言必须对应提案、证据、异议、交接、阻塞或结果之一。

## 8. 用户待决协议

### 8.1 何时必须升级

下面情况必须创建 `decision_request`：

- 两个方案都符合验收，但产品偏好不同。
- 需要改变原始范围、验收条件或优先级。
- 需要扩大文件、命令、网络、凭据或外部系统权限。
- 需要执行不可逆、高成本或对外动作。
- 公司已有事实互相冲突，员工不能判断哪条应被覆盖。
- 缺少只有老板知道的信息。
- 自动返工或协商已达到上限。

### 8.2 待决问题结构

```ts
type DecisionRequest = {
  id: string;
  workflowId: string;
  workItemId: string | null;
  askedByRoleId: string;
  question: string;
  options: { id: string; label: string; impact: string }[];
  recommendation: string;
  reason: string;
  blockingWorkItemIds: string[];
  status: "open" | "resolved" | "cancelled";
  answer: string;
};
```

### 8.3 暂停范围

待决问题只阻塞 `blocking_work_item_ids` 及其依赖后继。其他没有依赖该决定的工作项继续执行。

协作任务在存在开放待决问题且没有任何可运行工作项时进入 `waiting_user`；仍有可运行工作时保持 `collaborating`，但群聊顶部显示待决数量。

## 9. 协作任务状态机

建议状态：

```text
intake → planning → collaborating → verifying → review → applying → approved
                         │              │          │
                         ├→ waiting_user┘          ├→ returned → collaborating
                         ├→ failed                 └→ failed
                         └→ cancelled
```

| 状态 | 含义 |
| --- | --- |
| `intake` | 已收到老板消息，正在分类和建立上下文 |
| `planning` | 协调者正在拆工作项和验收条件 |
| `collaborating` | 员工正在讨论、执行、交接或复核工作项 |
| `waiting_user` | 所有可继续路径都依赖老板决定 |
| `verifying` | 汇总产出并执行协作任务级验收 |
| `review` | 验收包已生成，等待老板批准 |
| `applying` | 正在冲突检查和应用正式变更 |
| `approved` | 老板批准，产出已正式生效 |
| `returned` | 老板退回，等待协调者重开工作项 |
| `failed` | 系统或工具失败，无法自动恢复 |
| `cancelled` | 老板取消，不应用暂存产出 |

`returned` 不是终态。协调者根据退回原因重开原工作项或创建修正工作项后，协作任务回到 `collaborating`。

## 10. OPC MCP Server

### 10.1 定位

第四期新增一等工程组件 `OPC MCP Server`。它是所有智能体工具能力的统一入口：

```text
模型适配器
  → OPC 编排器
    → MCP Client / 权限网关
      → OPC MCP Server
        → ProjectWorkspace / RunWorkspace / Command Sandbox / Stores
```

模型适配器不再直接调用 `createProjectFileTools()`。它只接收当前工作项允许的 MCP 工具描述，并把工具调用交回 MCP Client。

### 10.2 传输

本机第一版使用 `stdio`：OPC 以受控子进程启动 MCP Server，适合当前单机部署，也避免额外开放网络端口。若以后拆到远程执行器，再增加 Streamable HTTP。

实现必须固定所支持的 MCP 协议版本，并通过官方 SDK 的兼容能力完成协商或请求构造。第四期不自造协议字段，也不依赖旧式 SSE 传输。

启动子进程时使用环境变量白名单，不能把 Next.js 进程中的全部密钥自动继承给 MCP Server。标准输出只用于 MCP 协议，诊断写标准错误并进入结构化日志。

### 10.3 进程与生命周期

- MCP Server 是独立 Node.js 入口，不嵌入 Route Handler。
- OPC 维护少量长期 MCP Client 连接，不为每次工具调用重复启动进程。
- 服务启动时完成工具发现并缓存工具清单。
- MCP Server 崩溃时，当前工具调用失败；编排器可重启一次，不能无上限重试。
- 协作任务状态保存在 MySQL 和 `.opc`，不能只存在 MCP 连接内存里。
- 每次工具调用都携带显式 `workflowId`、`workItemId`、`roleId` 和项目引用；服务端重新检查权限，不能只信任模型参数。

### 10.4 第一方工具

第四期首批工具：

| 工具 | 用途 | 风险级别 |
| --- | --- | --- |
| `opc.project.list_files` | 列出项目工作区文件 | 只读 |
| `opc.project.read_file` | 读取允许的 UTF-8 文本 | 只读 |
| `opc.project.stage_write` | 写入协作任务共享暂存区 | 可回滚写入 |
| `opc.project.get_diff` | 获取暂存差异 | 只读 |
| `opc.project.list_changes` | 获取协作任务修改清单 | 只读 |
| `opc.validation.run` | 运行已配置的验证配置 | 受控执行 |
| `opc.workflow.get_context` | 读取当前任务、工作项、决定和相关事件摘要 | 只读 |
| `opc.workflow.submit_artifact` | 登记产出、证据或报告 | 元数据写入 |
| `opc.workflow.request_decision` | 提交结构化老板待决问题 | 工作流写入 |
| `opc.workflow.handoff` | 请求把工作项交接给另一员工 | 工作流写入 |
| `opc.workflow.submit_for_review` | 提交工作项复核 | 工作流写入 |

状态变化工具只提交“请求”。MCP Server 调用应用层用例，由应用层检查当前状态、主责身份和依赖后再落库。

### 10.5 工具权限

每次调用必须同时通过四层检查：

1. 服务级：这个 MCP Server 是否启用。
2. 项目级：项目是否允许该工具或验证配置。
3. 员工级：角色和技能是否允许使用该工具。
4. 工作项级：当前工作项是否需要该工具，路径和动作是否在授权范围内。

权限结果分为：

```text
allow       直接执行
confirm     创建老板授权请求
deny        拒绝并记录原因
```

所有可回滚的项目暂存写入可以按策略 `allow`；任意命令、网络、正式文件应用和对外动作不得因为模型请求自动升级权限。

### 10.6 调用审计

每次 MCP 调用记录：

- Server、工具名和协议版本。
- 协作任务、工作项和员工。
- 参数的安全摘要；敏感字段脱敏。
- 开始、结束、耗时和结果状态。
- 输出摘要、产出引用和错误码。
- 权限决策及其依据。

大型输出保存在 `.opc/workflows/<workflowId>/tool-results/`，数据库只保存摘要、哈希、大小和相对引用。

### 10.7 外部 MCP Server

第四期只打基础能力：

- 在配置文件登记 Server 名称、启动方式、允许环境变量和启用状态。
- 启动后发现工具清单并保存快照。
- 老板按 Server 或具体工具启用。
- 默认权限为 `deny`。
- 工具描述变化时重新要求确认，防止同名工具静默扩大能力。
- 远程 Server 必须有明确地址、认证方式和网络授权；本期默认关闭。

外部 MCP Server 的工具不能绕过 OPC 权限网关，也不能直接获得数据库连接、项目绝对路径或全部环境变量。

## 11. 受控验证执行

### 11.1 验证配置

第四期不向模型开放任意命令字符串。项目通过受版本控制的配置声明允许的验证：

```json
{
  "profiles": {
    "unit-test": {
      "command": ["npm", "test"],
      "timeoutSeconds": 120
    },
    "typecheck": {
      "command": ["npm", "run", "typecheck"],
      "timeoutSeconds": 120
    },
    "build": {
      "command": ["npm", "run", "build"],
      "timeoutSeconds": 300,
      "requiresConfirmation": true
    }
  }
}
```

模型只能调用 `opc.validation.run({ profile: "unit-test" })`，不能传 `rm`、重定向、管道、子 shell或任意脚本正文。

### 11.2 验证工作区

验证必须看到暂存后的版本，但不能污染正式工作区。第四期为每个协作任务建立可执行沙箱：

```text
.opc/workflows/<workflowId>/
  before/
  after/
  sandbox/
  tool-results/
  manifest.json
```

执行验证前，将正式工作区加当前暂存覆盖层物化到 `sandbox/`。命令工作目录固定在沙箱根目录。验证产生的普通构建缓存不进入正式项目；需要作为产出的文件必须由员工显式登记并再次暂存。

### 11.3 资源限制

- 命令超时。
- 输出字节上限和截断提示。
- 子进程树取消。
- 最大并发数。
- 环境变量白名单。
- 固定工作目录。
- Windows 下验证最终绝对路径仍位于协作任务沙箱。
- 默认禁止网络；确需网络时必须由配置和老板授权同时允许。

## 12. 共享暂存与并发写入

第三期的暂存区以 `runId` 为单位。第四期改为以 `workflowId` 为单位，使多个员工看到同一份候选结果。

规则：

- 一个协作任务最多暂存 100 个文件（高于第三期单次执行 20 个文件的上限，因为一个协作任务可能拆成多个工作项，合计产出一个完整的站点或项目骨架）；新增内容合计仍不超过 5 MiB。
- 每个文件记录当前写入租约 `owner_work_item_id`。
- 员工写文件前获取租约；其他工作项只能读取，不能同时覆盖。
- 租约在工作项完成、交接、失败或超时后释放。
- 两个工作项确实需要改同一文件时，协调者显式安排先后依赖。
- 每次暂存写入记录基于哪个 `after_sha256`；版本不一致时拒绝覆盖并要求重新读取。
- 最终批准仍复查正式文件与最初 `before_sha256`，发现外部变化时停止应用。
- 所有工作项共享修改清单，但事件中保留每次修改的员工和工作项来源。

建议新增迁移 `db/migrations/007_collaboration.sql`，先新增结构并兼容读取旧表，不在同一次迁移中删除第三期数据。

保存每次工具调用的审计元数据，并关联项目、协作任务、工作项、员工和事件。

- `ProjectWorkspace` 继续是正式项目目录的唯一文件边界。

## 15. Agent 运行协议

每次员工被调度时获得最小必要上下文：

- 公司和项目的稳定事实摘要。
- 角色手册和技能。
- 当前协作任务目标与验收。
- 当前工作项、依赖和允许动作。
- 已解决的相关决定。
- 最近的相关公开事件，而不是无上限完整聊天记录。
- 当前可用 MCP 工具及权限说明。

员工输出使用结构化动作：

```ts
type AgentAction =
  | { type: "message"; text: string }
  | { type: "tool_calls"; calls: McpToolCall[] }
  | { type: "proposal"; workItems: WorkItemDraft[] }
  | { type: "objection"; targetId: string; reason: string; evidence: string[] }
  | { type: "handoff"; targetRoleId: string; reason: string }
  | { type: "decision_request"; request: DecisionRequestDraft }
  | { type: "submit_review"; summary: string; evidence: string[] };
```

硬限制：

- 单个员工每次调度最多 12 个模型回合。
- 单个工作项最多 30 次 MCP 工具调用。
- 单次工具调用默认 2 分钟，验证配置可以单独设置但不得超过 10 分钟。
- 连续 3 次相同调用且结果无变化时终止。
- 模型上下文按事件摘要裁剪，不直接无限追加所有历史和工具全文。
- 浏览器断开不取消服务端协作任务。

## 16. HTTP 与流式接口

建议接口：

```text
POST /api/projects/[id]/events
GET  /api/projects/[id]/events?after=<eventId>
GET  /api/projects/[id]/stream

GET  /api/workflows/[workflowId]
POST /api/workflows/[workflowId]/cancel
POST /api/workflows/[workflowId]/approve
POST /api/workflows/[workflowId]/return

POST /api/decisions/[decisionId]/resolve

GET  /api/mcp/servers
POST /api/mcp/servers/[serverId]/enable
POST /api/mcp/servers/[serverId]/disable
```

`POST /events` 保存老板消息后立即返回事件和路由结果。后续员工协作通过项目级 SSE 流持续推送。刷新页面时先按事件编号加载历史，再订阅新增事件。

批准、退回、取消和待决答复继续使用明确接口，不能通过自由文本猜测执行不可逆动作。老板可以在群聊中表达意图，但页面必须显示确认控件后才调用这些接口。

## 17. 页面设计

### 17.1 项目群聊

移除：

- “派给谁”下拉框作为必填前置步骤。
- “发送消息 / 执行任务”双按钮。
- 对话和执行两个互相割裂的主视图。

保留一个发送入口。时间线内嵌：

- 协作任务标题和状态。
- 员工认领、交接和复核。
- 折叠的工具活动。
- 待决卡片。
- 文件变更和验证摘要。
- 最终验收卡片。

页面顶部显示正在进行的协作任务数量和待老板决定数量。老板可展开任务侧栏查看工作项依赖、完整 diff 和审计记录。

### 17.2 工作项视图

工作项详情显示：

- 目标、验收和主责。
- 前置依赖和阻塞原因。
- 公开工作记录。
- MCP 工具调用摘要。
- 产出和验证证据。
- 复核结论。

工作项不是给老板逐项批准的额外负担。只有待决问题、高风险授权和最终协作任务验收需要老板操作。

### 17.3 看板任务

看板不再要求老板选择某一员工派工。选择公司和项目后，点击“交给项目团队”，系统创建协作任务。任务详情展示同一事件、工作项、待决和验收包。

看板任务与协作任务状态映射：

| 协作任务 | 看板任务 |
| --- | --- |
| `intake/planning/collaborating/verifying/waiting_user` | `doing` |
| `review/applying` | `review` |
| `approved` | `done` |
| `returned` | `doing` |
| `failed` | 保持 `doing`，显示失败原因 |
| `cancelled` | 回到 `inbox` 或保持原状态，由取消用例决定 |

## 18. 迁移策略

第四期不能直接删掉第三期流程。迁移分三步：

### 18.1 双读阶段

- 新建 `project_events`、`project_workflows` 和工作项表。
- 新群聊消息进入统一事件表。
- 旧 `project_messages` 和 `project_run_events` 通过适配器投影到新时间线。
- 第三期审批逻辑继续可用。

### 18.2 新任务切换

- 新任务全部创建 `project_workflow`。
- 单员工任务也作为只有一个工作项的协作任务运行。
- 文件工具改走 MCP Gateway。
- 旧 `project_runs` 只读，不再创建新记录。

### 18.3 收口阶段

- 把历史消息和执行事件迁移或生成稳定兼容视图。
- 移除页面对旧表的直接读取。
- 保留旧执行记录的审计和 diff，不删除用户历史。
- 确认没有活动旧执行后，再评估是否归档旧表和代码。

## 19. 测试策略

### 19.1 状态机和调度单元测试

- 普通交流不创建协作任务。
- 新任务创建协调者和初始工作项。
- 工作项依赖满足后才进入 `ready`。
- 环形依赖被拒绝。
- 非主责员工不能提交该工作项完成。
- 交接、复核、返工和取消状态合法。
- 等待老板决定时只暂停相关依赖链。
- 讨论、返工、模型回合和工具次数限制生效。

### 19.2 MCP 测试

- 工具发现结果稳定并校验 schema。
- stdio 协议输出不混入普通日志。
- 子进程只获得环境变量白名单。
- 缺少协作任务、工作项或员工身份时拒绝调用。
- 禁用工具和越权路径被拒绝。
- 工具超时、Server 崩溃和取消可以恢复为明确状态。
- 参数和结果中的敏感值被脱敏。
- 外部工具描述变化会使原授权失效。

### 19.3 文件和验证测试

- 多员工读取同一共享暂存结果。
- 两个工作项同时写同一路径时只有租约持有者成功。
- 基础版本哈希变化时拒绝覆盖。
- 验证沙箱能看到暂存文件，但正式目录保持不变。
- 验证命令不能使用管道、重定向、任意 shell 或工作区外路径。
- 超时后整个子进程树被终止。
- 批准前外部修改仍会阻止应用。

### 19.4 应用层集成测试

- 一条群聊任务自动拆给两名员工并完成交接。
- 员工出现事实分歧时先调用工具取证，不直接问老板。
- 产品分歧创建待决问题，老板答复后恢复正确工作项。
- 不相关工作项在等待决定期间继续运行。
- 全部工作项完成后生成完整验收包。
- 批准时文件应用和看板任务完成保持同一业务用例。
- 退回后正确重开工作项并保留原事件。

### 19.5 浏览器验收

- 群聊只有一个发送主动作。
- 发普通问题只得到回答，不启动执行。
- 发任务后相关员工自行分工，无需逐个选择。
- 群聊实时看到讨论、执行、验证和交接。
- 刷新后事件顺序、进行中状态和待决卡片不丢失。
- 老板回答待决问题后，页面显示采用的决定和恢复进度。
- 最终验收能查看 diff、验证证据和各员工贡献。
- 未批准前正式文件不变；批准后一次生效。

## 22. 风险与处理

| 风险 | 处理 |
| --- | --- |
| 所有员工一起回复导致噪音和成本失控 | 角色路由、只调度相关员工、讨论轮数和工作项上限 |
| 协调员工变成无约束总管 | 状态机和权限由应用层控制；协调者只提计划和汇总 |
| 多员工同时覆盖同一文件 | workflow 共享暂存、文件租约、版本哈希和显式依赖 |
| 模型把普通聊天误判成任务 | 可见路由结果、执行前可纠正、高风险工具仍需单独授权 |
| 员工频繁把问题推给老板 | 先证据、再规则、再专业主责；只有规定类型可以升级 |
| 待决问题让整个任务停住 | 只阻塞相关工作项及其依赖链 |
| MCP Server 获得过多本机权限 | 独立进程、环境白名单、固定工作区、工具级权限和默认拒绝 |
| 外部 MCP 工具描述被替换 | 保存 schema 哈希，变化后原授权失效并重新确认 |
| 命令执行造成破坏 | 只允许运行配置化 profile，固定沙箱，禁止任意 Shell 和默认网络 |
| 工具输出泄漏密钥 | 参数与结果脱敏、输出上限、密钥不进入模型上下文 |
| MCP 连接断开导致任务丢失 | 协作状态持久化，调用幂等，Server 只承担工具执行 |
| 验收只看员工自述 | 验收条件逐条绑定文件、测试、构建或其他可检查证据 |
| 第四期一次改动过大 | 先统一事件和状态机，再 MCP 化，再接真实多智能体和页面 |

## 23. 第四期验收场景

最终必须在真实浏览器和真实模型下走通：

1. 项目中加入策划、工程和运营三名员工。
2. 老板只在群聊发送：“给项目增加一个健康检查接口，补测试并更新使用说明。”
3. 系统创建协作任务，策划拆出实现、测试和文档工作项。
4. 工程通过 MCP 读取文件、暂存实现并运行允许的测试。
5. 运营在工程产出基础上更新说明，不能覆盖工程正在持有租约的文件。
6. 两名员工对接口失败响应存在分歧，先检查项目约定；若没有约定，创建带选项和推荐的待决问题。
7. 老板选择后，依赖项恢复，其他已完成工作不重跑。
8. 验证阶段展示测试通过数量、修改文件和每条验收结果。
9. 群聊出现最终验收卡片。
10. 批准前正式项目目录保持不变。
11. 老板批准后文件一次应用，协作任务为 `approved`，关联看板任务为 `done`。
12. 刷新页面后，完整讨论、工具摘要、老板决定、diff、验证和批准记录仍可追溯。

## 24. MCP 实现依据

第四期实现时以 MCP 官方规范和官方 SDK 为准。当前方案采用本机 `stdio`，远程场景预留 Streamable HTTP；协议状态不作为 OPC 协作任务的唯一存储，跨调用状态使用 OPC 自己的显式 ID 和持久化记录。
