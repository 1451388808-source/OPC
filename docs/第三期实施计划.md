## 1. 执行目标

本计划把第三期工程拆成可连续交付的工作包。每个工作包必须独立通过测试并保持现有看板、员工对话和项目对话可用。实施顺序以安全文件边界为先，再接模型，最后接任务状态机。

最终验收场景：

1. 在一条 `now` 任务中选择项目和员工。
2. 员工读取该项目工作区的文件并提出修改。
3. 正式文件在批准前保持不变。
4. 页面展示执行记录和文件差异。
5. 批准后文件生效，执行为 `approved`，任务为 `done`。
6. 外部修改造成哈希冲突时，批准停止且不覆盖文件。

## 3. 已确定的工程决策

### 3.1 执行编号

执行编号使用：

```text
r-<UUID>
```

数据库字段使用 `VARCHAR(40)`。执行不使用全局递增计数，避免后台并发执行争抢编号锁。

### 3.2 执行状态

完整状态为：

```text
queued → running → review → applying → approved
                    │          │
                    ├──────────┴─→ failed
                    └────────────→ returned
```

状态含义：

| 状态 | 含义 |
| --- | --- |
| `queued` | 已写入数据库，等待本机执行器接手 |
| `running` | 模型正在思考或调用文件工具 |
| `review` | 已生成结果，等待老板审批 |
| `applying` | 正在检查冲突并应用文件，按钮不可重复点击 |
| `approved` | 文件已应用，审批完成 |
| `returned` | 老板退回，保留执行记录和暂存内容 |
| `failed` | 模型、工具或应用恢复失败，需要人工处理 |

### 3.3 本机执行器

第三期先使用 Next.js 进程内的单并发执行队列，不增加独立 Worker 进程。接口为：

```ts
enqueueProjectRun(runId: string): void;
recoverInterruptedRuns(): Promise<void>;
```

`enqueueProjectRun` 写入队列后立即返回。浏览器断开不会取消执行。进程启动时，遗留的 `queued` 重新入队，遗留的 `running` 标记为 `failed`，错误写为“服务重启，执行中断”，不尝试从模型中间状态续跑。

队列实现保存在 `globalThis`，开发热更新时不得创建多个消费者。后续需要并行或远程执行时，再把这个模块替换成独立运行壳。

### 3.4 文件差异

第三期使用成熟的文本差异库生成 unified diff，不自行实现 diff 算法。计划采用 npm 包 `diff`。数据库只存文件元数据，修改前后正文保存在 `.opc/runs/<runId>/`。

## 4. 模块与接口

### 4.1 `ProjectWorkspace` 模块

Seam：`lib/project-workspace/index.ts`

```ts
export type ProjectRef = {
  companyId: string;
  projectId: string;
};

export function projectWorkspace(ref: ProjectRef): {
  ensure(): Promise<void>;
  list(input?: { path?: string; depth?: number }): Promise<WorkspaceEntry[]>;
  read(path: string): Promise<WorkspaceFile>;
};
```

该接口隐藏根目录计算、路径标准化、符号链接检查、忽略目录、UTF-8 校验、大小限制和哈希计算。调用方不能获取任意绝对路径。

### 4.2 `RunWorkspace` 模块

Seam：`lib/project-workspace/run-workspace.ts`

```ts
export function runWorkspace(input: ProjectRef & { runId: string }): {
  read(path: string): Promise<WorkspaceFile>;
  write(path: string, content: string): Promise<StagedChange>;
  changes(): Promise<StagedChange[]>;
  diff(path: string): Promise<string>;
  apply(): Promise<ApplyResult>;
};
```

`read` 优先读取本次执行的暂存版本。`write` 负责首份快照和 manifest。`apply` 负责全量冲突检查、原子替换和失败恢复。Route Handler 和模型适配层不得绕过这个模块直接使用 `fs`。

### 4.3 `ToolLoop` 模块

Seam：`lib/employees/tool-loop.ts`

```ts
export async function executeToolLoop(input: {
  runId: string;
  employee: RoleDefinition;
  context: string;
  tools: EmployeeToolset;
  limits: ToolLoopLimits;
  emit: (event: RunEventInput) => Promise<void>;
}): Promise<{ summary: string; changedPaths: string[] }>;
```

该接口隐藏 Provider 消息格式、工具结果回填、轮数统计、重复调用检测和完成摘要解析。应用层只关心执行结果，不解析 DeepSeek 的 `tool_calls`。

### 4.4 `ProjectRun` 应用模块

Seam：`lib/application/project-run.ts`

公开动作：

```ts
createProjectRun(input): Promise<{ runId: string }>;
loadProjectRun(runId): Promise<ProjectRunView>;
approveProjectRun(runId): Promise<void>;
returnProjectRun(runId, reason): Promise<void>;
dispatchTask(taskId, input): Promise<{ runId: string }>;
```

执行器调用内部函数 `performProjectRun(runId)`，不经 HTTP。所有状态迁移集中在这个模块；页面和 Route Handler 不能直接更新执行表。

## 5. 数据迁移

新增 `db/migrations/006_project_runs.sql`。

### 5.1 `project_runs`

关键约束：

- `project_id`、`role_id`、`request_text` 非空。
- `task_id` 可空。
- `status` 包含七个确定状态。
- 同一任务最多有一个 `queued`、`running`、`review` 或 `applying` 执行。MySQL 不直接使用部分唯一索引，由创建执行的事务锁住任务并检查。
- 保存 `summary`、`error_text`、`return_reason`、创建/更新时间和批准时间。

### 5.2 `project_run_events`

- 主键自增。
- 按 `(run_id, id)` 查询。
- `kind` 使用字符串列而不是数据库枚举，便于增加展示事件而不频繁改表。
- `body` 使用 JSON，应用层负责 Zod 校验。

### 5.3 `project_run_files`

- 主键 `(run_id, path)`。
- `operation` 为 `create` 或 `update`。
- 保存前后哈希和大小。
- 不保存文件正文。

### 5.4 任务关联

不向 `tasks` 表增加 `project_id` 或 `run_id`。任务与项目执行的关系由 `project_runs.task_id` 表达，避免任务模型被第三期执行细节污染。
