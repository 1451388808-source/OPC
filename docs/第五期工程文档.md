# OPC 第五期工程文档

版本：2026-10-13  
状态：草案，待确认后拆分实施  
范围：智能体可靠性、真实协商、独立复核、安全并行、研究能力、执行隔离与质量评估

## 0. 最终理想状态

OPC 的最终产品形态不是“老板分别操作多个智能体”，也不是“群聊里有几个会回复的机器人”。

它应该像一个真实项目群：

1. 老板在项目群里发出一项任务。
2. 项目里的相关智能体员工自己判断谁需要参与。
3. 员工在群里公开讨论目标、方案、分工、依赖、风险和验收方式。
4. 老板能够实时看到讨论过程，但不需要逐个点名员工或主持每一步。
5. 员工能自行解决的分歧，通过证据、角色职责和项目规则解决。
6. 员工无法决定的事项，在群里明确列出选项、影响和推荐，交给老板拍板。
7. 讨论收敛后，系统形成可执行计划，各员工按照分工开始工作。
8. 执行过程继续在群里展示：谁在做什么、使用了什么工具、产出了什么、验证是否通过、是否发生返工。
9. 员工完成后互相复核；发现问题则在团队内部退回修改，不立即打扰老板。
10. 全部验收满足后，团队在群里向老板提交最终交付包。
11. 老板查看结果、文件、验证证据和未解决风险，选择批准或退回。
12. 老板批准后，修改才正式生效，关联任务才完成。

完整业务主线：

```text
老板在群里发任务
  → 相关员工自动到场
  → 员工在群里讨论
  → 形成共识与工作计划
  → 员工按分工执行
  → 团队内部复核与返工
  → 在群里提交最终交付
  → 老板验收、批准或退回
```

老板在整个过程中只有三种必要动作：

- 发出任务或补充信息。
- 回答团队无法自行决定的问题。
- 验收最终交付。

其他调度、讨论、分工、执行和内部复核应由团队自行完成。

### 0.1 群聊中必须可见的内容

- 哪些员工参与了这项任务，以及参与原因。
- 对任务目标和验收条件的理解。
- 员工提出的方案和关键取舍。
- 对方案的异议、风险和支持证据。
- 最终采用的方案及原因。
- 工作项分工、依赖和预计产出。
- 员工认领、交接、阻塞和返工。
- 重要工具调用及结果摘要。
- 文件、研究笔记、验证报告等真实产出。
- 用户待决问题和老板答复。
- 最终验收报告和交付结果。

### 0.2 群聊中不展示的内容

“讨论过程可见”不等于展示模型的原始私有思维链。

群聊展示员工主动发布的工作内容：提案、理由、异议、证据、决定和进度。下面内容不直接展示：

- 模型逐 token 的私有推理。
- 没有形成工作价值的自言自语。
- 密钥、环境变量和敏感参数。
- 超长原始日志。
- 员工之间重复、无新证据的发言。

系统应把私有推理转成可审计的公开工作说明，而不是把隐藏思维直接倾倒进群聊。

### 0.3 讨论与执行不能再次分裂

第五期不能重新出现“聊天是一套流程、执行是另一套流程”的问题。

同一个 workflow 必须覆盖：

```text
讨论事件
  → 共识与计划
  → 工作项执行事件
  → 复核事件
  → 最终验收事件
```

用户不需要从群聊跳到另一个后台系统才能知道员工是否真的工作。详情页可以承载完整 diff、长日志和审计，但群聊必须始终能回答：

- 现在讨论到哪里。
- 最终决定了什么。
- 谁正在执行。
- 哪一项卡住。
- 是否已经验证。
- 什么时候需要老板介入。
- 最终交付在哪里。

### 0.4 第五期必须同时完成业务与技术两条线

第五期不是单纯的群聊界面改版，也不是只做底层重构。

必须同时交付：

| 业务线 | 技术线 |
| --- | --- |
| 老板只在群里发任务 | 路由不能误把普通询问当任务 |
| 员工讨论过程公开可见 | 讨论使用结构化事件，不保存原始思维链 |
| 员工自行分工和执行 | Agent Action、依赖和权限由状态机校验 |
| 员工自行解决分歧 | 协商有轮数、证据和收敛规则 |
| 无法决定时交给老板 | `request_decision` 在真实模型下稳定成功，不依赖 UUID |
| 执行进度在群里可见 | MCP 调用具有错误码、审计和幂等键 |
| 团队内部复核和返工 | 复核员工独立读取文件并重跑验证 |
| 最终结果交给老板验收 | diff、验证和引用均有可检查证据 |
| 多名员工真正协作 | 无冲突工作项安全并行，相同文件自动串行 |
| 服务中断后继续工作 | attempt、检查点和恢复不会重复成功动作 |
| 自主运行不会失控 | token、时间、返工和并发预算强制生效 |
| 研究员工能查外部资料 | 联网工具只读、带引用并防提示注入 |

以下任一种情况存在时，第五期都不能标记完成：

- 群聊看起来在讨论，但员工没有真实执行工具。
- 文件已经产生，但群聊没有展示讨论、分工和复核过程。
- 模型用自然语言声称完成，但没有工具证据。
- 用户待决 UI 存在，但真实 `request_decision` 仍会参数失败。
- 页面支持并行状态，但后台仍只有单任务串行队列。
- 验证按钮存在，但项目缺配置时仍允许进入最终验收。
- 重启后可以恢复状态，但会重复执行已经成功的工具调用。
- 外部 MCP 管理页面存在，但 schema 变化后旧授权仍然有效。

## 1. 背景

第四期已经建立完整的本机协作链：

- 群聊单入口和统一事件流。
- 模型生成工作项计划。
- 员工按依赖认领和执行。
- OPC MCP Server 提供文件、暂存、diff、验证和待决工具。
- 工作项复核、用户仲裁和最终验收。
- 看板任务与 workflow 联合审批。

系统已经从“单员工文件执行器”跨到“受控多智能体工作流”，但当前智能体成熟度仍处于 Beta。工程结构是完整的，真实模型行为还不够稳定。

现有真实运行暴露了下面的问题：

1. 普通能力询问可能被识别成任务，智能体因此创建没有必要的说明文件。
2. 协调模型可能生成语法正确但业务价值低的计划，或者回退成单工作项。
3. `request_decision` 要求模型填写内部 work item UUID；真实调用曾因参数不匹配失败。
4. 项目没有 `opc-validation.json` 时，员工无法运行验证，只能报告“无法验证”。
5. 复核员工当前主要检查完成摘要和证据文本，没有独立读取文件、运行命令或复现结果。
6. 多员工在数据模型上可以并行，但当前后台队列主要顺序执行，不是真正的安全并发。
7. 员工间的“讨论”主要表现为计划、执行和退回，不是有提案、异议、证据和收敛规则的真实协商。
8. 研究员工没有受控联网检索工具，不能完成真正的外部研究与来源核验。
9. 模型工具调用失败时，错误信息不够结构化，模型容易重复错误或改用文字绕开工具。
10. 服务重启后工作项会恢复为 `ready` 并重新执行，不能从最近一个可靠检查点续跑。
11. 没有 workflow 级 token、时长、模型费用和返工预算，长期自主运行可能成本失控。
12. 外部 MCP Server 有表结构和默认拒绝策略，但缺少完整的配置、授权、版本变化和密钥管理体验。
13. 验证沙箱限制路径、环境和命令，但没有 OS 或容器级网络与资源隔离。

第五期要解决的不是“再加更多工具”，而是把第四期的受控自治变成可长期使用、能解释失败、能独立验收、成本可控的可靠自治。

## 2. 第五期目标

第五期完成后，一条真实任务应具备下面的质量：

1. 系统只有在高置信度且目标明确时自动创建任务；不确定时先询问或显示确认，不静默开工。
2. 协调员工输出的计划必须通过业务校验、能力覆盖检查和依赖检查。
3. 智能体使用领域级动作，不需要知道数据库 UUID、状态字段和内部表结构。
4. 工作项主责可以使用 MCP 完成工作；工具错误会返回稳定错误码和可修复提示。
5. 多个无冲突工作项可以真正并行执行，文件、验证和模型预算仍受控。
6. 员工意见不一致时走“提案 → 异议 → 证据 → 收敛或升级”协议，而不是重复发言。
7. 复核员工使用独立、只读的 MCP 上下文重新检查文件和验证结果，不只阅读主责自述。
8. 工程类工作项没有成功验证证据时，不能自动进入最终验收。
9. 研究员工能够使用获批的联网研究 MCP，结论逐条带来源、时间和引用。
10. 用户待决工具在真实模型下稳定成功，老板答复后准确恢复依赖链。
11. 服务重启、模型超时和 MCP 崩溃后，从持久化检查点恢复或明确失败，不重复不可重放动作。
12. 每个 workflow 有 token、模型调用、工具调用、时长和返工预算；超限时暂停并说明原因。
13. 外部 MCP Server 只有经过登记、工具审查和授权后才能使用，schema 变化会自动撤销旧授权。
14. 页面能清楚区分“正在执行”“等待员工复核”“等待老板决定”“验证失败”和“预算耗尽”。

这些能力最终必须服务于第 0 节的业务闭环。第五期不能只在数据库里证明工作项完成；老板必须能够在群聊时间线中看见团队如何从讨论走到交付。

第五期完成标志：真实模型连续完成一组覆盖聊天、工程、研究、待决、返工、并行和重启恢复的基准任务，关键成功率达到本文定义的质量门槛，没有静默越权、虚假验证或无限重试。

## 3. 第五期原则

### 3.1 可靠性优先于自治程度

宁可停下来确认，也不能错误地自动执行。宁可明确报告“缺验证配置”，也不能用完成摘要替代验证证据。

### 3.2 模型提出领域动作，系统解析内部身份

模型不再直接填写：

- `workflowId`
- `workItemId`
- 项目绝对路径
- 数据库状态
- MCP Server 内部 id

模型表达“阻塞当前工作项及其后继”“把工作交给工程”“请求老板选择方案 A/B”。应用层负责把领域表达解析成内部编号。

### 3.3 主责自述不是验收证据

文件存在、测试通过、来源可靠等结论必须由工具结果、哈希、验证运行或独立复核支撑。

### 3.4 并行必须由依赖和资源证明安全

并行不是同时启动多个模型。只有文件集合不冲突、依赖满足、资源预算允许的工作项才能进入并行执行。

### 3.5 每次失败必须可分类

不能只保存“工具调用失败”。失败至少分类为：

```text
invalid_input
permission_denied
stale_version
lease_conflict
missing_configuration
validation_failed
provider_timeout
provider_rejected
budget_exceeded
server_unavailable
internal_error
```

模型只对可修复错误重试。权限、预算和配置错误必须暂停或升级。

### 3.6 老板仍保留最终验收和高风险授权

第五期不会移除最终批准，也不会让智能体自行执行对外发送、部署、付费或不可逆动作。

## 4. 质量门槛

第五期验收使用明确指标，不以“看起来更聪明”为标准。

| 指标 | 门槛 |
| --- | --- |
| 明确普通交流误建任务率 | 小于 2% |
| 明确任务未创建 workflow 率 | 小于 2% |
| 模型计划一次通过结构校验率 | 大于 95% |
| `request_decision` 真实调用成功率 | 100% |
| 工具参数错误自动修复率 | 大于 90%，最多重试 2 次 |
| 工程任务独立验证覆盖率 | 100% |
| 复核员工独立读取或验证比例 | 100% |
| 无证据任务进入最终 review | 0 次 |
| 同一路径并发覆盖 | 0 次 |
| schema 变化后沿用旧 MCP 授权 | 0 次 |
| 单 workflow 无限循环 | 0 次 |
| 重启后重复已确认外部动作 | 0 次 |
| 预算超限后继续调用模型 | 0 次 |

评估集至少包含 50 条固定用例，并保留真实失败回放。

## 5. 本期范围

### 5.1 必须实现

- 消息路由 v2：高置信自动执行、中置信确认、低置信交流。
- 可纠正的路由结果和误判回放集。
- 结构化 Agent Action 协议。
- 领域引用解析层，模型不接触内部 UUID。
- 结构化错误码与工具调用修复提示。
- 真实员工协商协议。
- 支持最多 2 个工作项安全并行。
- 独立复核执行器和只读 MCP 工具集。
- 验证 profile 检测、配置模板和强制证据规则。
- 用户待决工具真实模型稳定性修复。
- 联网研究 MCP 及引用产出。
- 外部 MCP Server 配置与授权页面。
- workflow 检查点与恢复策略。
- 模型、工具、token、时长和返工预算。
- 固定评估集、回放和质量报告。
- OS/容器级验证隔离方案至少落地一种。

### 5.2 明确不做

- 自动发布、部署、付款或代表用户对外发送。
- 移除老板最终审批。
- 无限制并行和无限后台运行。
- 让智能体自行安装任意软件。
- 默认信任远程 MCP Server。
- 允许研究工具把网页内容直接当作系统指令。
- 把原始私有思维链作为协作记录。

## 6. 消息路由 v2

### 6.1 三态路由

路由结果改为：

```ts
type MessageRoute =
  | { type: "conversation"; confidence: number }
  | { type: "new_workflow"; confidence: number; title: string }
  | { type: "needs_confirmation"; confidence: number; proposedType: "conversation" | "new_workflow" }
  | { type: "workflow_input"; workflowId: string }
  | { type: "decision_answer"; decisionId: string };
```

规则：

- 高置信度任务才自动创建 workflow。
- 中置信度显示“按交流回复 / 创建任务”二选一，不调用模型员工和工具。
- 能力询问、解释、状态查询默认是交流。
- “做什么”“能做什么”“怎么看”不得仅凭动作词判定为任务。
- 用户手动选择始终覆盖自动路由。

### 6.2 路由证据

每次路由保存：

- 分类结果。
- 置信度。
- 使用的规则或模型版本。
- 用户是否纠正。
- 最终采用结果。

被用户纠正的消息自动进入评估回放集。

## 7. Agent Action v2

### 7.1 领域动作

```ts
type AgentAction =
  | { type: "speak"; text: string }
  | { type: "call_tool"; tool: string; arguments: unknown }
  | { type: "propose_plan"; items: WorkItemProposal[] }
  | { type: "raise_objection"; targetKey: string; reason: string; evidenceRefs: string[] }
  | { type: "handoff"; targetRole: string; reason: string }
  | { type: "request_decision"; scope: "current" | "current_and_dependents"; question: string; options: DecisionOption[]; recommendation: string }
  | { type: "submit_review"; summary: string; evidenceRefs: string[] }
  | { type: "report_blocked"; code: string; detail: string };
```

### 7.2 引用解析

模型只使用：

- 工作项 `key`
- 角色 id
- artifact ref
- 当前工作项、后继工作项等相对作用域

应用层将它们转换成 UUID。转换失败时返回 `invalid_reference`，并列出允许值，不让模型猜 UUID。

### 7.3 Schema 驱动

计划、待决、复核和工具动作均使用 JSON Schema 或 Provider 的结构化输出能力。禁止依赖“从自然语言中截取第一个 JSON 对象”作为主要协议。

无法使用原生结构化输出的 Provider 必须经过严格解析、一次修复和失败停机。

## 8. 工具错误与修复协议

MCP Gateway 统一返回：

```ts
type ToolFailure = {
  ok: false;
  code: string;
  message: string;
  retryable: boolean;
  correction?: {
    allowedValues?: string[];
    expectedSchema?: unknown;
    currentSha256?: string;
  };
};
```

示例：

- 决策工具不接受模型传 work item UUID；只接受 `scope`。
- 验证 profile 缺失时返回可用 profile 列表和配置入口。
- 文件版本过期时返回最新 SHA，并要求重新读取。
- 工具权限不足时 `retryable = false`，不得重复调用。

同类错误最多修复 2 次。第三次进入 `blocked` 或 `failed`。

## 9. 真实协商协议

### 9.1 协商事件

员工讨论不再是自由文本轮流回复，而是以下事件：

```text
proposal
objection
evidence
response
consensus
escalation
```

### 9.2 收敛规则

1. 协调员工提出计划。
2. 受影响角色各有一次异议机会。
3. 异议必须指出具体工作项、风险和所需证据。
4. 能用工具解决的先取证。
5. 专业职责明确时由主责或复核角色决定。
6. 两轮后仍无法收敛，创建用户待决。

没有新证据的重复发言被系统拒绝，不进入模型上下文。

### 9.3 讨论预算

- 初始计划讨论最多 2 轮。
- 每个角色每轮最多 1 条公开发言。
- 单条异议不超过 500 字。
- 讨论 token 单独计入 workflow 预算。

## 10. 独立复核

### 10.1 复核工具集

复核员工获得只读工具：

- `list_files`
- `read_file`
- `get_diff`
- `list_changes`
- `run_validation`
- `read_artifact`

不能调用 `stage_write`。若需要修改，必须退回主责。

### 10.2 复核输入

复核员工看到：

- 原始工作项目标和验收。
- 当前暂存文件和 diff。
- 验证运行原始摘要。
- 主责提交的证据引用。

复核员工不直接继承主责的私有推理，只继承公开事实。

### 10.3 复核输出

```ts
type VerificationReport = {
  verdict: "approve" | "return" | "blocked";
  checks: {
    acceptance: string;
    status: "passed" | "failed" | "not_checked";
    evidenceRefs: string[];
    note: string;
  }[];
  reason: string;
};
```

所有验收项均为 `passed` 才能批准。`not_checked` 不能按通过处理。

## 11. 验证配置与证据

### 11.1 配置模板

项目创建时可生成 `opc-validation.json` 模板。系统根据项目文件提供建议：

- `package.json`：建议 `test`、`typecheck`、`build`。
- Python 项目：建议 `pytest`、类型检查。
- 纯静态项目：建议 HTML 解析、链接检查。
- 纯文档项目：建议文件存在、标题和字数检查。

建议配置必须由老板批准后进入正式工作区，模型不能暂存一份配置后立即利用它扩大命令权限。

### 11.2 强制验证规则

- 工程工作项存在文件修改时，至少需要一个成功验证 profile。
- 没有适合的 profile 时，工作项进入 `blocked: missing_configuration`，不提交最终验收。
- 验证失败不能被完成摘要覆盖。
- 每次验证保存配置哈希、候选文件哈希、命令、退出码和输出摘要。

### 11.3 隔离

第五期将验证从 Next.js 子进程迁移到独立 Runner，至少提供：

- 文件系统只挂载 workflow 沙箱。
- 默认禁止网络。
- CPU、内存、进程数和磁盘上限。
- 超时后终止完整进程树。
- 不继承应用密钥。
- 运行镜像或运行环境版本可追溯。

本机优先实现容器 Runner；容器不可用时，明确降级为“无网络隔离保证”，并要求用户确认。

## 12. 安全并行调度

### 12.1 并行条件

两个工作项同时执行必须满足：

- 依赖已完成。
- 预期写入路径集合不相交。
- 不使用互斥验证资源。
- workflow 并发预算允许。
- 模型 Provider 并发限制允许。

### 12.2 写入意图

计划阶段工作项声明：

```ts
type WriteIntent = {
  includes: string[];
  excludes: string[];
};
```

未知写入范围默认不能并行。实际申请文件租约时再次校验。

### 12.3 调度

默认最多 2 个执行工作项并行，复核不计入文件写入并发但受模型并发预算限制。

调度器使用 worker lease，避免多进程重复认领。lease 包含过期时间和心跳，不能只依赖单进程内存队列。

## 13. 研究能力

### 13.1 联网研究 MCP

为研究员工提供只读研究工具：

- 搜索官方来源。
- 打开指定页面。
- 读取公开文档。
- 保存来源元数据。

默认域名策略：

- 官方文档和一手来源优先。
- 远程页面内容始终视为不可信数据。
- 页面指令不能改变系统提示词、权限和工作流。
- 不自动登录、不提交表单、不上传文件。

### 13.2 引用产出

研究结论使用结构化引用：

```ts
type ResearchCitation = {
  url: string;
  title: string;
  publisher: string;
  retrievedAt: string;
  excerptHash: string;
};
```

每句结论关联至少一条引用。来源不可访问或冲突时进入“不确定”，不能写成公司事实。

## 14. 外部 MCP 管理

### 14.1 配置来源

外部 MCP Server 不允许由模型自由填写命令。老板在管理页登记：

- Server 名称。
- stdio 命令或远程地址。
- 允许的环境变量。
- 认证引用。
- 项目范围。

### 14.2 工具审查

首次发现工具时展示：

- 工具名和描述。
- 输入 schema。
- 风险级别。
- 是否读文件、写文件、联网或执行命令。

老板按工具选择 `allow / confirm / deny`。

### 14.3 Schema 漂移

工具描述或 schema 哈希变化后：

- 原授权自动暂停。
- 时间线产生安全事件。
- 老板重新审查后才能调用。

## 15. 检查点与恢复

### 15.1 Attempt 模型

工作项一次执行不再只靠 `retry_count`，新增 attempt：

```text
work_item
  └─ attempt 1
       ├─ model round
       ├─ MCP call
       ├─ checkpoint
       └─ result
```

每次重试创建新 attempt，不覆盖旧记录。

### 15.2 检查点

检查点保存：

- 当前 Agent Action 序号。
- 已完成工具调用及其幂等键。
- 模型上下文摘要。
- 当前暂存 manifest 哈希。
- 尚未完成的动作。

服务重启后从最后一个完整检查点恢复。模型回合中断时重跑该回合，但已成功的幂等工具调用不重复执行。

### 15.3 不可重放动作

外部发送、付款、部署等未来动作必须具有明确幂等键和用户批准记录。第五期仍不执行这些动作，但数据模型要能区分 `replayable` 与 `non_replayable`。

## 16. 预算与成本控制

每个 workflow 配置：

```ts
type WorkflowBudget = {
  maxModelCalls: number;
  maxToolCalls: number;
  maxInputTokens: number;
  maxOutputTokens: number;
  maxDurationSeconds: number;
  maxReworkRounds: number;
  maxConcurrentAgents: number;
};
```

预算规则：

- 达到 80% 时在群聊显示提醒。
- 达到 100% 时进入 `waiting_user`，不得继续调用。
- 重试、复核和讨论均计入预算。
- 页面按员工、工作项和 Provider 展示用量。
- Provider 未返回 token 统计时使用本地估算并标记 `estimated`。

## 20. 测试与评估

### 20.1 消息路由

- 能力询问不创建任务。
- 明确交付请求创建任务。
- 模糊请求进入确认。
- 用户纠正后结果持久化。

### 20.2 计划

- 角色覆盖与依赖正确。
- 不使用项目外员工。
- 不生成自依赖或环。
- 写入范围冲突会串行化。

### 20.3 工具修复

- `request_decision` 不需要模型提供 UUID。
- 缺失验证 profile 返回明确错误和可用选项。
- stale hash 触发重新读取而不是重复写入。
- permission denied 不重试。

### 20.4 独立复核

- 主责虚报测试通过时，复核实际运行失败并退回。
- 主责漏文件时，复核能发现。
- 复核不能写文件。
- 未检查验收不能批准。

### 20.5 并行

- 不同文件的两个工作项并行成功。
- 相同文件意图自动串行。
- worker 崩溃后 lease 过期并恢复。
- 同一工作项不会被重复执行。

### 20.6 恢复

- 模型超时从检查点重试。
- MCP 调用成功但响应丢失时通过幂等键恢复。
- 重启不重复验证或文件写入。

### 20.7 评估运行

新增命令：

```powershell
npm run eval:routing
npm run eval:planning
npm run eval:tools
npm run eval:e2e
```

每次模型、提示词、路由器或工具 schema 变化必须运行相关评估。

## 22. 最终验收场景

### 场景 A：交流不误执行

老板问：“你们现在能做什么？”系统直接回答能力，不创建 workflow、不写文件。

### 场景 B：真实多角色任务

老板要求：“研究现有接口约定，实现健康检查，补测试并更新说明。”

系统应：

1. 群聊显示协调员工召集研究、工程和复核员工。
2. 研究与工程在群里公开各自对目标、依赖和风险的判断。
3. 员工对接口方案提出异议时，群聊显示异议、证据和最终共识。
4. 群聊显示形成的工作计划，研究和工程工作项正确拆分。
5. 研究先完成并带来源，完成摘要与产出路径出现在群聊。
6. 工程读取研究产出并实现，群聊显示认领、文件修改和验证进度。
7. 验证 Runner 成功运行测试，结果摘要出现在群聊。
8. 复核员工独立读取 diff 并重跑测试；复核过程和结论可见。
9. 若复核退回，群聊显示退回原因、返工过程和再次复核结果。
10. 最终验收逐条显示证据，团队在群里正式向老板交付。

验收时，老板不查看数据库也能从群聊回答：员工讨论了什么、采用了什么方案、谁完成了哪部分、验证是否通过、最终产出在哪里。

### 场景 C：待决问题

员工遇到两个都可行的接口命名方案。模型只提交 `scope = current_and_dependents`，系统解析内部工作项。老板点击选项后恢复执行，连续 20 次无 schema 或 UUID 错误。

### 场景 D：并行

工程修改代码，运营同时准备说明；二者文件集合不相交并行执行。若两者临时申请同一路径，后申请者等待而不是覆盖。

### 场景 E：虚假证据

主责声称测试通过，但验证实际失败。独立复核必须退回，workflow 不能进入最终 review。

### 场景 F：重启

员工完成一次 MCP 写入后服务重启。系统从检查点恢复，不重复写入，不丢暂存，不重新执行已成功的幂等工具调用。

### 场景 G：预算

模型连续返工达到预算。系统进入 `waiting_user`，显示已用 token、调用次数、失败原因和继续所需授权。

## 23. 风险与处理

| 风险 | 处理 |
| --- | --- |
| 结构化输出仍被 Provider 破坏 | 原生 schema、严格解析、一次修复、失败停机 |
| 路由过于保守 | 中置信确认，不用降低安全门槛换自动率 |
| 独立复核增加成本 | 只对需要证据的工作项复核，纳入预算 |
| 并行造成文件冲突 | 写入意图、lease、动态冲突检测 |
| 联网研究受提示注入 | 页面视为数据，工具只读，来源隔离，不执行页面指令 |
| 验证容器启动慢 | 复用基础镜像和缓存，不复用可写沙箱 |
| 外部 MCP 偷换 schema | schema 哈希变化自动撤权 |
| 检查点泄漏敏感上下文 | 摘要脱敏，正文按引用存储 |
| token 成本失控 | workflow 预算、80% 提醒、100% 强制暂停 |
| 评估集被实现过拟合 | 保留隐藏用例和真实失败回放 |

## 24. 第五期之后

第五期稳定后再评估：

1. 受控 Git commit、push 和部署审批。
2. 定时任务与长期监控代理。
3. 多主机 Runner 和远程工作区。
4. 多用户账号和组织权限。
