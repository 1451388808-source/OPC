## 1. 执行目标

第五期把第四期已经跑通的“受控多智能体工作流”提升为可长期运行的可靠自治系统。实施不以增加页面或工具数量为完成标准，而以以下事实为准：

1. 普通交流不会静默创建任务。
2. 模型只提交领域动作，不填写 workflow、work item 等内部编号。
3. 工具失败有稳定错误码、是否可重试和纠正信息。
4. 文件修改、验证、复核和最终验收均有独立证据。
5. 并行、重试、恢复和预算由应用状态机强制执行。
6. 群聊持续展示提案、决定、分工、执行、复核和交付，不展示私有思维链。

第四期现有 workflow、统一事件流、共享暂存区和本机 MCP 继续作为迁移基础。第五期采用增量迁移，不重写已经通过验收的业务闭环。

## 2. 已确定的工程决策

### 2.1 按风险分层实施

第五期按下面顺序推进：

```text
评估基线
  → 领域动作和错误协议
  → 路由与验证门槛
  → 独立复核与真实协商
  → 安全并行与研究 MCP
  → 检查点、恢复和预算
  → 真实模型验收
```

前一层没有确定性测试时，不把真实模型接到后一层。

### 2.2 内部身份只由系统注入

模型可见并可提交的引用限定为：

- 工作项计划中的稳定 `key`。
- `current`、`current_and_dependents` 等相对作用域。
- 角色 id 和 artifact ref。

`workflowId`、`workItemId`、数据库状态和项目绝对路径由编排器或 MCP Gateway 注入。模型给出未知引用时返回 `invalid_reference` 和允许值，不允许猜测 UUID。

### 2.3 证据与状态分离

“员工说完成”只是一条公开消息，不直接构成验收证据。第五期把以下对象分别持久化：

- Agent Action：员工提出了什么动作。
- MCP 调用：工具实际执行了什么。
- Verification Run：哪个候选版本在什么环境通过了什么 profile。
- Verification Report：复核员工逐条如何判断验收。
- Project Event：哪些结论需要在群聊中展示。

### 2.4 兼容迁移

新增迁移从 `010_agent_reliability.sql` 开始。旧 `retry_count`、现有复核摘要和现有 MCP 审计在对应第五期表启用前继续可读；新代码不得产生两套互相矛盾的事实。

## 3. 工作包

### W0：失败样本与评估基线

依赖：无。

修改范围：

```text
evals/message-routing.jsonl
evals/decision-request.jsonl
evals/tool-repair.jsonl
lib/collaboration/evaluator.ts
scripts/eval-*.ts
package.json
```

步骤：

1. 把第四期暴露的误路由、待决参数失败、重复工具错误和虚假验证固化为用例。
2. 每条用例包含稳定编号、输入、预期结果和问题来源。
3. 先记录当前实现基线，不为提高分数修改预期答案。
4. 评估输出总数、通过数、失败样本和分类指标，并以非零退出码表示门槛失败。
5. 最终扩展到不少于 50 条固定用例，真实失败追加到回放集。

完成条件：

- 第五期每个已知问题至少有一个可重复失败用例。
- `npm run eval:routing` 可以在无模型、无数据库条件下运行。
- 需要真实 Provider 的评估明确区分“未配置”和“失败”，不能静默跳过。

### W1：Agent Action、引用解析与工具错误

依赖：W0 可运行。

修改范围：

```text
lib/collaboration/action-protocol.ts
lib/collaboration/reference-resolver.ts
lib/mcp/error.ts
lib/employees/mcp-tools.ts
lib/employees/tool-loop.ts
mcp/server-factory.ts
lib/application/collaboration.ts
```

步骤：

1. 用 Zod 定义 Provider 无关的 Agent Action v2。
2. 为计划、待决、异议、交接、阻塞和复核动作定义严格 schema。
3. 实现相对作用域到内部工作项的解析器。
4. 把 `request_decision` 的模型参数从 `blockingWorkItemIds` 改为 `scope`。
5. MCP Gateway 继续注入当前 workflow/work item/role，MCP Server 在服务端解析阻塞范围。
6. 定义稳定 ToolFailure 代码、`retryable` 和纠正信息。
7. 工具循环把结构化错误返回模型；不可重试错误立即停止，同类可修复错误最多修复两次。

完成条件：

- 模型工具 schema 中不出现 workflow/work item UUID。
- `current_and_dependents` 能解析当前工作项及全部未结束后继。
- 未知引用返回 `invalid_reference`，权限错误不会重试。
- Fake Provider 和真实 Provider 的待决请求均不再要求模型生成内部编号。

### W2：消息路由 v2

依赖：W0、W1。

步骤：

1. 路由结果改为 `conversation / new_workflow / needs_confirmation / workflow_input / decision_answer`。
2. 规则优先识别能力询问、解释、状态查询和讨论请求。
3. 中置信结果只生成确认卡，不创建 workflow、不调用员工和工具。
4. 保存分类、置信度、规则版本、用户纠正和最终结果。
5. 用户显式选择始终覆盖自动路由。

完成条件：

- 明确普通交流误建任务率小于 2%。
- 明确任务漏建率小于 2%。
- 浏览器中可以纠正分类，纠正结果进入回放集。

### W3：验证配置与独立 Runner

依赖：W1。

步骤：

1. 检测项目类型并生成待批准的 `opc-validation.json` 建议。
2. 没有适用 profile 时返回 `missing_configuration`，工作项进入 blocked。
3. 新增独立 Runner 进程和客户端协议。
4. 容器可用时默认无网络、限制 CPU/内存/进程/磁盘且不继承应用密钥。
5. 容器不可用时标记降级环境，未经用户确认不能声称网络隔离。
6. 保存配置哈希、候选 manifest 哈希、环境版本、退出码和输出引用。

完成条件：

- 工程文件有修改但没有成功 Verification Run 时不能进入最终 review。
- 超时会终止完整进程树。
- 验证不会改变正式项目目录。

### W4：独立复核

依赖：W3。

步骤：

1. 为复核员工提供只读 MCP 工具集。
2. 复核上下文只包含原始目标、验收、候选 diff、验证结果和主责证据。
3. 复核员工逐条生成 Verification Report。
4. `failed` 或 `not_checked` 退回主责；复核员工不能写文件。
5. 最终验收卡展示主责证据和独立复核结论。

完成条件：

- 主责虚报测试通过、漏文件和证据错配都被拦截。
- 需要独立复核的工作项 100% 至少读取文件、diff 或重新运行验证。

### W5：真实协商

依赖：W1、W4。

步骤：

1. 新增 `proposal / objection / evidence / response / consensus / escalation` 事件。
2. 协调者提案后，只调度受影响角色提出一次结构化异议。
3. 异议必须关联工作项 key、风险和证据需求。
4. 能用工具验证的分歧先取证；职责明确的低风险决定由主责记录结论。
5. 两轮无共识时使用领域级待决动作升级老板。
6. 拒绝没有新证据的重复发言。

完成条件：

- 三个固定冲突场景分别能自动收敛或正确升级。
- 群聊能看到采用方案、反对意见、证据和最终原因。

### W6：安全并行

依赖：W1、W3、W5。

步骤：

1. 工作项计划增加 WriteIntent。
2. 根据依赖、写入意图、验证资源和 Provider 限流计算并行批次。
3. 新增数据库 worker lease、过期时间和心跳。
4. 默认最多两个执行工作项并行。
5. 实际写入时继续使用文件租约二次防护。

完成条件：

- 两个不同文件工作项真实并行执行。
- 相同或未知写入范围不会并行。
- worker 崩溃后 lease 可恢复，同一工作项不会重复认领。

### W7：研究与外部 MCP

依赖：W1、W5。

步骤：

1. 提供只读搜索、打开页面、读取公开文档和保存来源元数据工具。
2. 页面内容始终作为不可信数据，不得改变提示词、权限或工作流。
3. 研究结论绑定结构化引用和获取时间。
4. 项目设置提供 MCP Server 登记、工具审查、风险和授权策略。
5. 工具描述或 schema 哈希变化后暂停旧授权并产生安全事件。

完成条件：

- 研究任务关键结论均可追溯到来源。
- 远程工具默认无权限，schema 漂移后旧授权使用次数为零。

### W8：检查点、恢复与预算

依赖：W1-W7 的稳定事件和工具协议。

步骤：

1. 新增 work item attempt、agent action、checkpoint 和 model usage 表。
2. 每次重试创建新 attempt，不覆盖旧失败。
3. MCP 调用增加幂等键和 replayable 标记。
4. 保存动作序号、已完成工具调用、上下文摘要和暂存 manifest 哈希。
5. 重启从完整检查点恢复，已成功工具调用不重复。
6. 强制执行模型、工具、token、时长、返工和并发预算。
7. 80% 显示提醒，100% 进入 waiting_user 并停止调用。

完成条件：

- 重启、模型超时、MCP 响应丢失和预算耗尽用例全部明确恢复或停止。
- 不可重放动作没有批准和幂等记录时不能执行。

3. 修复所有 P0/P1 可靠性问题。
4. 更新 README、功能需求、运维说明和第五次工程总结。
5. 记录质量指标、已知限制和下一期入口。

完成条件：

- 第五期工程文档第 4 节全部质量门槛通过。
- 第 22 节最终验收场景全部有可检查证据。
- 没有静默越权、虚假验证、重复外部动作或无限循环。

  workflow_budgets

  verification_runs
  verification_reports

- 每个迁移都有 MySQL 集成测试和回滚说明；生产不自动执行破坏性回滚。
