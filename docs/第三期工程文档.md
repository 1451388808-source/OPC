# OPC 第三期工程文档

版本：2026-10-12
状态：已完成；W0-W9 已实现并验证
范围：项目文件执行、任务派工、文件差异审批

具体工作包、依赖顺序和完成条件见 [第三期实施计划](./第三期实施计划.md)。

## 1. 背景

OPC 当前已经具备这些能力：

- 本机看板管理任务、本周重点和决策，MySQL 是主要数据源。
- 可以添加员工，为员工配置角色手册、技能和模型。
- 可以创建公司和项目，把员工加入项目。
- 项目成员共享一段对话，并通过 DeepSeek 流式回复。
- 员工能维护自己对项目的短期判断，但不能访问项目文件，也不能真正完成工程或文档工作。

第三期要跨过的边界是：员工从“只在对话里给建议”变成“能在受限项目目录里读取和生成工作成果”，同时继续由老板决定哪些修改正式生效。

本文以当前代码为基线。旧文档里“当前仍处于第一期”“模型尚未接入”等描述已经落后，第三期开工前需要同步修正公司事实和 README。

## 2. 第三期目标

第三期完成后，一条项目工作应能走完下面的闭环：

1. 老板在项目对话或任务详情中选择一名员工并下达工作。
2. 系统把公司目标、项目上下文、角色手册、技能、任务目标和验收条件交给员工。
3. 员工只能在该项目的工作目录内列文件、读文件和提出文件修改。
4. 所有修改先进入隔离的暂存区，不立即覆盖正式文件。
5. 页面展示执行摘要、工具记录、文件列表和逐文件差异。
6. 执行结果停在“待批准”。
7. 老板批准后，系统检查文件没有被其他操作改动，再把暂存内容应用到项目目录。
8. 退回时保留原因，员工可以基于原执行上下文继续修改。

第三期的完成标志：一条工程任务可以从看板派给员工，员工读取项目文件并生成修改，老板看到差异后批准，正式文件才发生变化，任务最终进入 `done`。

## 3. 核心原则

### 3.1 人工批准是提交边界

模型可以分析、起草和生成修改，但不能自行把任务标记为完成。正式文件变化和任务完成必须由老板批准。

### 3.2 项目目录是唯一文件边界

每个项目的工作目录固定由编号推导：

```text
workspaces/<companyId>/<projectId>/
```

例如：

```text
workspaces/c-001/p-001/
```

第三期不允许在页面里填写任意本机路径。项目名称不参与路径计算，避免重命名和特殊字符改变文件位置。

### 3.3 先暂存，后应用

员工的 `write_file` 不直接写正式工作目录，而是写到一次执行独有的暂存目录：

```text
.opc/runs/<runId>/
  before/        # 修改前快照
  after/         # 员工提出的新内容
  manifest.json  # 路径、哈希、操作类型和大小
```

`.opc/` 必须加入 `.gitignore`。数据库保存执行状态和元数据，文件内容保存在本机暂存目录，避免把大段源码塞进 MySQL。

### 3.4 一条执行只有一名主责员工

项目可以有多名员工，但一次文件执行只指定一名主责。需要其他角色参与时，新开执行或先在共享对话里讨论，避免多个模型同时修改同一批文件。

### 3.5 应用前检查并发变化

读取文件时记录 SHA-256。批准应用前再次计算正式文件哈希；若文件已经变化，则停止应用并提示“文件已变化，需要重新执行或重新确认”，不能静默覆盖。

## 4. 本期范围

### 4.1 必须实现

- 为每个项目建立固定工作目录。

- 读取 UTF-8 文本文件。

### 4.2 明确不做

- 删除、移动和重命名文件。

- 自动 `git commit`、`git push`、部署或发送消息。
- 定时任务、长期后台代理和无限自主循环。
- 图片、音频、视频等二进制文件编辑。

这些能力应在文件读写闭环稳定后分别开新阶段，不和第三期同时实现。

## 5. 用户流程

### 5.1 从项目对话发起

1. 老板打开项目。
2. 在群聊输入区选择一名在场员工。
3. 输入要求，点击“执行任务”；“发送”仍然只用于讨论。
4. 页面显示员工正在读取哪些文件、提出哪些修改。
5. 执行结束后显示“待批准”和文件差异。
6. 老板批准或填写原因退回。

普通“发送消息”和“执行工作”必须是两个明确动作。普通消息只产生对话，不获得文件工具；执行工作才创建 `project_run`。

### 5.2 从任务发起

1. 老板打开一条 `inbox` 或 `doing` 任务。
2. 选择公司、项目和项目内员工。
3. 点击“交给员工”。
4. 系统创建与任务关联的执行，并把任务调整为 `doing`。
5. 员工完成暂存修改后，任务进入 `review`。
6. 任务详情显示执行摘要、差异和验收条件。
7. 批准任务时先应用文件，再把任务改为 `done`。
8. 退回任务时执行记录变为 `returned`，任务回到 `doing`，退回原因写入 `notes`。

任务批准与文件应用必须是一个用例，避免文件已经生效但任务仍未完成。

## 6. 文件工具

第三期只向模型开放三个工具。

### 6.1 `list_files`

输入：

```json
{ "path": ".", "depth": 3 }
```

输出相对路径、类型和文本文件大小。默认深度为 2，最大深度为 5，最多返回 500 项。忽略 `.git`、`.next`、`node_modules`、`.opc` 和隐藏缓存目录。

### 6.2 `read_file`

输入：

```json
{ "path": "src/app.ts" }
```

读取正式目录中的当前内容；若本次执行已经暂存过该路径，则读取暂存后的内容。返回相对路径、文本、字节数和 SHA-256。

单文件最大 1 MiB。包含 NUL 字节或无法按 UTF-8 解码时，按二进制文件拒绝读取。

### 6.3 `write_file`

输入：

```json
{
  "path": "src/app.ts",
  "content": "完整文件内容"
}
```

写入暂存目录，不写正式目录。第一次修改某路径时保存修改前快照和哈希。工具返回 `created` 或 `updated`、新文件大小和新哈希。

第三期使用完整文件内容，不设计字符串查找替换协议。完整内容更容易验证、生成差异和重放，代价是限制单文件大小。

## 7. 文件安全边界

所有文件入口必须经过同一个 `ProjectWorkspace` 模块，Route Handler、模型工具和批准用例不能各自拼路径。

路径规则：

- 只接受 `/` 分隔的仓库相对路径。
- 拒绝空路径、绝对路径、盘符、UNC 路径、NUL 字符和 `..`。
- 解析后的绝对路径必须仍在项目根目录下。
- 从项目根到目标文件的所有已存在路径段都执行 `lstat`，发现符号链接立即拒绝。
- `.git`、`.next`、`node_modules`、`.opc` 和隐藏系统目录不可访问。
- 文件名和目录名分别设置长度上限，完整相对路径建议不超过 500 字符。
- 单次执行最多修改 20 个文件，新增内容合计不超过 5 MiB。（第四期起，协作任务级别的共享暂存改用更高的上限，见第四期工程文档第 12 节。）
- 写暂存文件采用临时文件加原子重命名。

审批应用规则：

1. 锁定执行记录。
2. 确认状态为 `review`。
3. 检查每个正式文件的当前哈希与 `before_sha256` 一致。
4. 为所有目标准备同目录临时文件。
5. 逐个原子替换；失败时用 `before` 快照恢复已经替换的文件。
6. 全部成功后把执行标记为 `approved`。
7. 若关联任务，同一用例继续更新任务和导出副本。

文件系统和 MySQL 不能形成真正的单一事务，因此必须保留执行日志、恢复快照和可重试状态。不得只靠数据库事务假装文件写入也能自动回滚。

## 8. 数据模型

新增迁移建议为 `db/migrations/006_project_runs.sql`。

### 8.1 `project_runs`

| 字段 | 含义 |
| --- | --- |
| `id` | `r-` 加递增编号或 UUID |
| `project_id` | 所属项目 |
| `task_id` | 可空；从任务发起时填写 |
| `role_id` | 主责员工 |
| `request_text` | 老板的原始要求 |
| `status` | `queued`、`running`、`review`、`applying`、`approved`、`returned`、`failed` |
| `summary` | 员工对本次结果的简短说明 |
| `error_text` | 失败原因 |
| `created_at` | 创建时间 |
| `updated_at` | 更新时间 |
| `approved_at` | 批准时间，可空 |

### 8.2 `project_run_events`

记录执行过程，便于刷新页面后恢复，而不是只依赖浏览器内存中的 SSE：

| 字段 | 含义 |
| --- | --- |
| `id` | 自增编号 |
| `run_id` | 所属执行 |
| `kind` | `reasoning`、`tool_call`、`tool_result`、`message`、`error` |
| `body` | JSON 或文本内容 |
| `created_at` | 创建时间 |

思考过程可展示但不参与批准判断。批准依据是工作要求、工具结果、文件差异和验收条件。

### 8.3 `project_run_files`

| 字段 | 含义 |
| --- | --- |
| `run_id` | 所属执行 |
| `path` | 项目内相对路径 |
| `operation` | `create` 或 `update` |
| `before_sha256` | 新文件为空值 |
| `after_sha256` | 暂存内容哈希 |
| `before_size` | 修改前大小 |
| `after_size` | 修改后大小 |

文件正文不进入表中。`run_id + path` 为唯一键。

## 9. 模型执行循环

当前 `EmployeeModel.run` 只返回文本。第三期需要把模型适配层扩展为统一的工具调用协议，DeepSeek 的具体响应格式不能泄漏到应用层。

建议的领域类型：

```ts
type EmployeeToolCall = {
  id: string;
  name: "list_files" | "read_file" | "write_file";
  arguments: unknown;
};

type EmployeeStep =
  | { type: "text"; text: string }
  | { type: "reasoning"; text: string }
  | { type: "tool_calls"; calls: EmployeeToolCall[] };
```

执行循环：

1. 构建系统提示词和工作上下文。
2. 调用模型。
3. 模型若返回工具调用，逐个校验参数并执行。
4. 把工具结果追加到模型上下文，同时持久化事件。
5. 继续调用模型，直到模型给出完成摘要或达到限制。
6. 检查至少有一项有效产出；有文件修改则生成差异并进入 `review`。

硬限制：

- 最多 20 轮模型调用。
- 最多 50 次工具调用。
- 最长运行 10 分钟。
- 连续 3 次完全相同的工具调用直接失败。
- 工具参数解析失败可以把错误返回模型修正，但同类错误最多 3 次。
- 浏览器断开不取消服务端执行；刷新后从事件表恢复状态。

系统提示词必须明确：只能通过工具得知文件内容；没有工具结果时不得声称已经查看或修改文件；完成摘要要列出修改路径并对照验收条件。

## 10. 应用层划分

建议新增：

```text
lib/project-workspace/
  path.ts                 # 路径标准化与边界检查
  workspace.ts            # list/read/stage write
  manifest.ts             # 快照、哈希和暂存清单
  apply.ts                # 冲突检查、应用与恢复

lib/application/
  project-run.ts          # 创建、执行、读取执行状态
  approve-project-run.ts  # 批准纯项目执行
  return-project-run.ts   # 退回执行
  dispatch-task.ts        # 从任务创建执行
  approve-task-run.ts     # 应用文件并批准任务

lib/employees/
  tools.ts                # 模型可见工具定义
  tool-loop.ts            # Provider 无关的执行循环
  deepseek.ts             # DeepSeek 请求、流式和工具调用解析

lib/infrastructure/
  project-run-store.ts    # 三张执行表的 SQL
```

依赖方向：

- 页面和 Route Handler 只调用 `lib/application`。
- `lib/application` 组织数据库、模型和文件模块。
- `project-workspace` 不依赖 React、HTTP 或模型 Provider。
- DeepSeek 适配层不直接操作文件。
- 文件工具只能调用 `project-workspace`，不能使用裸 `fs` 拼接用户路径。

## 11. HTTP 与流式接口

建议接口：

```text
POST /api/projects/[id]/runs
GET  /api/project-runs/[runId]
GET  /api/project-runs/[runId]/events
POST /api/project-runs/[runId]/approve
POST /api/project-runs/[runId]/return
POST /api/tasks/[id]/dispatch
```

`POST /runs` 只负责创建执行并返回 `runId`。执行过程使用 SSE 推送，也写入 `project_run_events`。刷新页面后，先 GET 当前状态和历史事件，再继续订阅新增事件。

现有 `/api/projects/[id]/messages` 继续只负责普通项目对话，不在同一个接口里隐式获得文件权限。

## 12. 页面设计

### 12.1 项目页

项目页增加两个视图标签：

- `对话`：保留当前共享对话。
- `执行`：显示执行列表和当前执行详情。

对话输入区同时提供“发送”和“执行任务”。执行任务要求选择一名主责员工，创建成功后自动进入对应执行详情。

执行过程同时出现在群聊时间线中：老板的任务、员工思考、工具调用、工具结果、完成摘要和修改文件持续追加。执行在服务端后台继续，离开或刷新页面后从执行表和事件表恢复；执行页仍用于完整 diff 和审批。

DeepSeek 工具回合使用流式响应。`reasoning_content` 和最终回复按增量写入事件表，前端合并连续增量并显示执行中光标；工具调用作为思考段之间的独立步骤。

执行详情包含：

- 原始要求、主责员工和运行状态。
- 当前步骤和工具活动。
- 员工完成摘要。
- 修改文件列表。
- 每个文件的差异视图。
- “批准应用”和“退回修改”按钮。

按钮必须使用明确文字。批准前显示修改文件数；存在哈希冲突时禁用批准并说明具体路径。

### 12.2 任务详情

增加“交给员工”区域：

- 公司选择。
- 项目选择。
- 项目成员选择。
- 派工按钮。

任务关联执行后，详情页显示执行进度。进入 `review` 后，现有批准区同时展示文件差异。批准时只出现一个主按钮，不要求用户先批准执行、再批准任务两次。

## 13. 任务状态与执行状态

| 场景 | 任务状态 | 执行状态 |
| --- | --- | --- |
| 从任务派工成功 | `doing` | `running` |
| 员工完成暂存修改 | `review` | `review` |
| 老板批准 | `done` | `approved` |
| 老板退回 | `doing` | `returned` |
| 模型或工具失败 | 保持 `doing` | `failed` |
| 文件发生并发冲突 | 保持 `review` | `review`，标记冲突 |

纯项目执行没有关联任务时，只改变执行状态，不创建隐藏任务。后续若发现所有执行都需要任务追踪，再单独讨论是否自动建任务。

## 14. 测试策略

### 14.1 纯单元测试

- 正常相对路径通过。
- `..`、绝对路径、盘符、UNC 和 NUL 被拒绝。
- 符号链接逃逸被拒绝。
- 文件数量、大小、深度和轮数限制生效。
- 新建和更新操作判断正确。
- 哈希冲突阻止应用。
- 部分应用失败时可以从快照恢复。
- 重复工具调用和超限循环会终止。

### 14.2 应用层测试

- 创建执行后写入正确的项目、员工和任务关联。
- 工具事件和模型消息按顺序持久化。
- 完成执行会把任务改为 `review` 并写入 `artifacts`。
- 批准时先应用文件，成功后任务才进入 `done`。
- 应用失败时任务不进入 `done`。
- 退回原因写入任务记录和执行记录。

### 14.3 浏览器验收

- 项目普通对话不会产生文件权限。
- 点击执行后，刷新页面仍能看到运行状态。
- 执行完成后能查看创建文件和修改文件的差异。
- 未批准前正式项目文件保持不变。
- 批准后文件内容与差异中的新版本一致。
- 文件被外部改动后批准会显示冲突，不覆盖文件。
- 从任务派工、待批准、批准完成的整条路径可运行。

完成标准：员工能自行列文件、读文件、暂存至少一个文件并给出摘要。

### P3-4：批准与退回

- 实现冲突检测、文件应用、失败恢复。
- 实现执行批准和退回页面。

完成标准：未批准不落正式文件；批准后正确落盘；冲突时绝不覆盖。

### P3-5：任务派工闭环

- 任务关联项目和执行。
- 从任务详情派给员工。
- 把执行摘要、文件路径和审批合并进任务状态机。

完成标准：一条真实工程任务从 `doing` 经员工执行进入 `review`，老板一次批准后文件生效且任务进入 `done`。

### P3-6：稳定性与清理

- 补齐应用层和浏览器测试。
- 清理过期暂存执行，保留已批准执行的元数据。
- 增加运行超时、错误恢复和可读日志。
- 更新交接文档和部署说明。

完成标准：连续执行、刷新、退回、重跑和冲突场景均可恢复，没有项目目录越界。

## 17. 风险与处理

| 风险 | 处理 |
| --- | --- |
| 模型读取或覆盖项目外文件 | 所有路径只经过 `ProjectWorkspace`；拒绝绝对路径、`..` 和符号链接 |
| 模型误改大量文件 | 暂存、文件数和总大小上限、人工差异审批 |
| 老板查看差异期间文件被改 | 记录并复查 SHA-256，冲突时停止应用 |
| 浏览器断开导致执行丢失 | 执行和事件持久化；SSE 只负责实时展示 |
| 模型无限调用工具 | 轮数、工具数、超时和重复调用限制 |
| 文件应用一半失败 | 修改前快照、原子替换、应用日志和恢复流程 |
| 任务完成但文件未生效 | 文件应用成功后才更新任务为 `done` |
| 第三期范围膨胀 | 只做文本文件工具；执行命令、MCP、Git 和部署另开阶段 |
| 开发时再次出现 ChunkLoadError | 同一工作区只运行一个开发服务，不让 `next dev` 与 `next build` 并发写 `.next` |

## 18. 第三期之后

第三期稳定后再评估：

1. 受控命令执行和测试运行。
2. Git 差异、提交和推送审批。
3. 部署、发送消息等对外动作。
4. 将文件和命令工具拆成 MCP 或独立运行壳。
5. 多人账号、远程访问和权限系统。

优先顺序保持为：

```text
稳定现有系统
  → 项目文件安全读写
  → 暂存与差异审批
  → 任务派给员工
  → 受控命令执行
  → Git、部署和对外动作
```
